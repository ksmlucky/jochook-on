## 지금 할 일 — 여기부터 보기 (2026-10-14)

선수·경기 관리, 팀 접속, 감독·코치 권한, 필터와 변경 이력을 구현했고 **[Northflank 공개 서버](https://http--jochook-on-web--wmjz5mzg84j4.code.run/) 배포·실제 DB 이전·로그인 검증을 완료**했다. 다음은 아이폰 실기기 설치와 HANA FC 운영진·소수 회원의 시범 사용이다. 실제 기록은 공개 주소에서 입력하며 로컬 DB와 자동 동기화되지 않는다.

1. **실제 경기 한 건 대조 — 사용자 중심**: 이미 등록된 경기 중 한 건을 골라 카카오톡 투표·실제 출석·1~4쿼터 출전·득점·도움·스코어가 맞는지 확인한다. 아직 없는 경기라면 실제 자료로 한 건 입력한다. 정정할 내용이 있다면 저장 후 변경 이력의 작업자·시각·전후 내용도 확인한다. 확인만을 위해 실제 기록을 임의로 바꾸지는 않는다. 입력 방법은 [README의 경기 기록 안내](../README.md#경기-기록-사용하기)를 참고한다.
2. **배포 전 검증·소스 정리 — 완료**: 2026-10-14 22시 재검증에서 Java 207개·Docker MySQL 89개·프론트 41개를 통과했고 개인정보·비밀번호 제외를 확인했다. 최신 기능을 GitHub `main`의 `a619334`로 업로드했고 Linux CI의 frontend/backend가 모두 통과했다. Linux AMD64 웹/API Docker 이미지 빌드도 성공했다. ARM64 서버 실행은 별도 확인한다. [검증 기록](verification.md)
3. **무료 서버 배포 — 완료, 운영 백업 후속**: US Central의 API·웹·비공개 TLS MySQL 8.4.11이 Running이다. 실제 15개 테이블을 이전하고 전체 행 지문 일치, HTTPS·기존 감독 로그인·쿠키·CSRF·팀 격리·전달 헤더 처리를 검증했다. 최초 암호화 백업은 복구 검증했고, 이후 클라우드 변경을 보호할 자동 백업은 무료 적용 조건 확인 후 구성해야 한다. [배포·백업 안내](northflank-deployment.md). Oracle 도쿄 A1은 AD-1 용량 부족이며 **6시간 정기 확인**을 유지한다. 예약 확인에는 PC와 Codex 앱이 켜져 있어야 하지만 이미 배포한 앱 접속에는 PC가 필요하지 않다. Oracle 확보 후 ARM 실행·복구·운영 부담을 확인해 이전 여부를 정한다. 도메인 구매 없이 Northflank HTTPS 주소를 사용한다.
4. **휴대전화 시범 사용 — 사용자·팀 운영진**: 공개 HTTPS 주소에서 아이폰 Safari 접속 → 팀 코드·비밀번호 입력 → 홈 화면 추가 → 재접속을 확인한다. 감독·코치의 기록 수정, 회원의 조회 권한도 실기기로 확인한다. 이후 소수 팀원과 사용하고 불편한 점을 수집한다. [모바일 앱 계획](mobile-app-plan.md)

그다음은 실사용 불편 개선과 시즌 득점·도움·출석 통계다. 여러 포메이션 지원 이후 다른 팀 도입을 검토하며, 가상 몸값·프로 선수 비교는 후순위를 유지한다. 스토어 베타 배포는 개발자 계정 비용과 빌드 환경을 결정한 뒤 진행한다.

## 경기 기록 삭제 (2026-10-14)

- 감독·코치가 경기 목록에서 삭제 전 확인창을 거쳐 하루 전체 기록을 삭제한다. 선수 명부는 보존하고 수정 충돌·다른 팀 접근을 차단한다. [기능 명세·화면 흐름](match-deletion.md), [실행한 검증](verification.md)
- 선수단의 실제 존재하는 연령대·직책·1지망 포지션 그룹(공격/미드/수비/키퍼)을 AND로 필터링하며 전체 DB 결과에 정렬·페이징을 적용한다. 변경 이력에 한국 시간 기준 변경 일시를 초까지 표시한다.
- 경기 등록·수정·삭제 전후와 서버 인증 작업자를 V19 `match_record_events`에 남기고 감독·코치용 변경 이력 화면에서 비교한다. 사용자가 선택한 운영 정책은 직접 수정 + 이력 관리이며 승인 절차는 도입하지 않는다. [기능 명세·스토리보드](player-filters-and-match-history.md)

## 운영 범위와 확장 순서 (2026-10-14 확정)

- 당분간 실제 사용 팀은 **HANA FC 한 팀**으로 제한한다. 현재 스쿼드 계획·자동 편성이 4-1-2-3에 고정되어 있으므로 다른 팀 도입은 여러 포메이션 지원 이후 진행한다.
- 팀 생성·운영진 지정·코드 접속·팀별 데이터 분리는 확장 기반으로 유지한다. 서비스 관리자는 공개 팀 모집을 시작하지 않으며, 개발 검증용 팀은 실제 회원 DB와 분리한 임시 DB에서만 만든다.
- 순서는 **HANA FC 실사용과 운영 피드백 → 포메이션 선택·수동 스쿼드·자동 편성·쿼터 기록·엑셀의 일관된 확장 → 다른 팀 시범 도입**이다.
- 포메이션별 자리와 선호 포지션 매핑, 쿼터별 저장 방식, 기존 4-1-2-3 기록 호환을 먼저 정의한다. 기존 GK 그룹·출전 균등·연속 휴식·교체·출석 우선 규칙이 새 포메이션에서도 지켜지는지 검증한다. 지원할 포메이션 종류는 다음 기획에서 정한다.
- Oracle Cloud·Cloudflare 배포와 아이폰 접속은 HANA FC의 실사용을 위해 준비하며 다른 팀 공개 시점과 별개다. 이전 AWS 계획에서 변경됐고 Cloudflare 가입은 완료, Oracle 도쿄의 로그인·Free Tier 상태도 확인했다. A1 생성은 용량 부족으로 실패하여 무료 VM 확보와 실제 배포는 미완료다. 도메인은 가격 검토만 허용됐으며 아직 구매하지 않았다.

- [x] 01~04 단계 탭, 단계 이동 시 초안 유지, 하단 고정 저장 버튼으로 스크롤 줄이기

현재 4쿼터는 고정이며 길이·교체 시각은 저장하지 않는다. 교체는 같은 자리의 1:1 교체만 지원하고 재투입·같은 쿼터의 포지션 이동은 지원하지 않는다. 비어 있는 배치 자리는 미기록으로 남긴다. 엑셀 반영은 기존 4쿼터 초안을 교체하며 투표·실제 출석을 자동 변경하지 않는다. 자동 편성은 경기 전 계획만 채우고 분 단위 추정·프로 환산은 하지 않는다. 참석자의 출전 명단이 없어도 실제 출석은 보관한다.

완료 기준: 실제 모임 하루의 기록을 운영진이 입력하고, 화면의 개인 집계가 원본 기록과 일치한다.

- [x] 서비스 관리자 팀 생성·운영진 지정, 팀별 데이터 분리와 활성 소속 검증, 기존 HANA FC 연결

포트폴리오에는 기능 소개뿐 아니라 요구사항, 설계 선택 이유, 문제 재현, 검증 결과, 개선 전후 수치를 남긴다. Redis·Kafka·Kubernetes·Spring Batch는 해결할 문제가 생겼을 때 도입 근거를 검토한다.

## 자동 편성 — 경기 입력 단계로 앞당겨 구현

사용자 요청에 따라 기본 자동 편성을 경기 기록 입력 흐름에 추가했다. 자세한 정책과 계산 구조는 [자동 편성 설명](automatic-lineup.md)을 따른다.

- [x] 참석 예정 명단 확인 버튼으로 1~4쿼터 4-1-2-3 계획 자동 생성
- [x] 1~3지망 중 GK가 있는 선수를 GK 전용 그룹으로 분리, 한 명이면 4쿼터 전담
- [x] 같은 쿼터 중복 출전 금지, 같은 자리 1:1 교체는 각각 0.5쿼터
- [x] 두 쿼터 연속 휴식 금지, 그룹 내 총 출전량 차이 최대 1쿼터
- [x] 1~3쿼터 교체 최소화 우선, 필요한 교체는 4쿼터에 우선 배치
- [x] 남는 출전량은 과거 실제 출석률 순으로 배정, 동률은 추첨
- [x] 선호 100/60/30 점수, CB·CM 두 자리 대응, 비선호 배치 알림
- [x] 출석률·개인 출전량·휴식·쿼터별 교체 수 표시

- [x] 인원 부족/GK 없음/포지션 미확인/계산 시간 제한 경고와 단위·MySQL 검증

## 5단계 — 마지막 기능 확장

### 5-1. 자동 편성 고도화

- [ ] 선수별 가능한 쿼터, 고정 배치와 당일 참석 변경 반영
- [ ] 대회 기준 연도와 연령대별 정원 (생일 없이 기준 연도 − 생년)
- [ ] 다른 포메이션, 가중치 조절, 시즌/최근 기간 출석률 정책
- [ ] 편성 근거·정책 버전·시드·출석률 스냅샷 영구 저장과 재현
- [ ] 후보 비교와 포지션 최적화 성능 개선

선호 선택지는 LB/CB/RB/CDM/CM/LW/ST/RW/GK를 유지하며 선호 미확인은 임의로 추정하지 않는다. 현재 인원 전체를 참석 처리하지 않고 운영진이 실제 투표 명단을 선택한다.
### 5-2. 프로 선수와 기록 비교 (가장 마지막)

- [ ] **출전 4쿼터 = 비교용 1경기**를 후보로 검토. 아직 확정·구현하지 않으며 기존 2쿼터=45분 초안은 적용하지 않음
- [ ] 팀 경기 수와 선수 개인의 출전량 중 어떤 분모를 쓸지 결정. 현재 개인 기록은 교체한 두 선수 각각 0.5쿼터로 보존
- [ ] 확정한 기준에 따라 프로 선수의 90분 경기당 득점·도움과 비교할 지표 설계. 쿼터 길이·실제 출전 분은 수집하지 않음
- [ ] 비교 화면에 출전 쿼터, 적용 기준과 비교 기간을 함께 표시하고, 경기 수준 차이를 고려한 재미용 기록 비교로 설명
- [ ] 프로 선수 기록의 데이터 출처·이용 조건·갱신 주기와 최소 출전량 기준 결정

완료 기준: 실제 기록을 보존하면서 환산 근거를 확인할 수 있고, 같은 기간·지표 기준으로 조기축구 선수와 프로 선수의 기록을 비교할 수 있다. 출전량이 0이거나 불명확한 경우에는 환산 지표를 계산하지 않는다.

## 외부 용병 참가 — 기본 구현과 후속 정책

인원이 부족하면 외부 용병을 초청해 경기를 진행할 수 있다. 사용자 요청에 따라 02에서 등록·재선택하는 기본 흐름을 구현했다.

- 용병은 실제 경기에 참가하는 외부 참가자이며, 테스트용 더미 데이터로 처리하지 않는다.
- 이름은 있지만 등번호는 없는 상태로도 참가할 수 있어야 한다. 없는 등번호에 임의의 번호를 부여하지 않는다.
- [x] MEMBER/GUEST 구분과 같은 ID 재참가, 회원 목록에서 분리, 선호 기반 자동 편성·경기 기록 연결
- [ ] 용병 전용 프로필 수정·활동 종료, 회원 전환과 동명이인 병합 정책
- 출석·시즌 순위·시상·가상 몸값에 포함할지는 별도 정책으로 결정한다.
