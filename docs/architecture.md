# 구조와 설정 이유

## 제품과 팀의 구분

**조축ON**은 서비스 이름이고 **HANA FC**는 현재 소속 팀의 이름입니다. 영문 코드명은 `jochookOn`, 저장소·패키지 slug는 `jochook-on`을 사용합니다. Java 시작점은 `com.jochookon.JochookOnApplication`, 프론트 패키지는 `@jochook-on/web`입니다.

이번 변경은 이름과 팀 표시를 분리하는 범위입니다. 실제 팀 생성·공유 코드 접속·팀별 데이터 분리는 다음 단계이며, 현재 DB에 `teams`나 팀 소속 검사 기능이 생긴 것으로 보지 않습니다. 화면 흐름과 인수 기준은 [브랜드 변경 명세](rebranding.md)에 정리했습니다.

설정의 기본 이름은 `JOCHOOK_ON_*` 환경변수와 `jochookon.bootstrap.admin.*` Spring 속성을 사용하고 기존 `HANA_*`·`hana.*` 설정은 호환 입력으로 유지합니다. 실제 DB·사용자·볼륨과 로컬 경로는 그대로 연결합니다. Java 패키지·제품 이름을 바꾸는 데 테이블 변경은 필요하지 않으므로 기존 Flyway SQL을 수정하지 않습니다.

## 한 저장소, 하나의 백엔드

프론트엔드와 백엔드를 같은 Git 저장소에 둡니다. 기능 하나를 바꿀 때 API와 화면 변경을 함께 확인할 수 있고, 혼자 개발하는 프로젝트의 관리 부담이 작습니다. 실행 프로그램은 React 개발 서버와 Spring Boot API로 나눕니다. 여러 서버로 기능을 분리하는 작업은 현재 필요하지 않습니다.

## 요청 하나를 따라가기

```text
App.tsx
  → usePlayers.ts                    화면의 로딩·실패·성공 상태
  → api.ts                           GET /api/v1/players
  → Vite의 /api 프록시                개발 중에만 8080으로 전달
  → SecurityConfig                   허용한 조회 요청인지 검사
  → PlayerController                 page·size를 검증
  → PlayerQueryService               읽기 트랜잭션과 정렬 기준
  → PlayerRepository                 JPA 조회
  → MySQL players                    실제 저장된 선수
  → PlayerPageResponse               화면에 필요한 값만 응답
  → PlayerDirectory                  선수 목록 또는 빈 화면
```

회사에서 사용하는 구조와 비교하면 Controller는 비슷하고, MyBatis Mapper의 역할 일부를 Repository가 담당합니다. Entity는 DB 행과 연결되는 객체입니다. 응답 DTO는 Entity와 분리해 내부 필드나 연관관계가 API 응답에 그대로 노출되지 않게 합니다. JPA를 사용하더라도 실제 SQL과 실행계획을 이해하고 검토해야 합니다.

## 기능별 폴더

`player/` 안에 선수 관련 Controller·Service·Repository·Entity를 함께 둡니다. 나중에 `attendance/`, `match/`, `valuation/`이 생겨도 각 기능을 한곳에서 찾을 수 있습니다. 지금은 계층마다 별도 Gradle 모듈을 만들거나 인터페이스를 추가하지 않습니다. 실제 의존관계가 복잡해지는 시점에 구조를 조정합니다.

## 중요한 설정

| 설정 | 이유 |
| --- | --- |
| Java toolchain 21 | 개발자와 CI의 컴파일 기준을 맞춘다. JDK를 자동 설치하는 설정은 아니다. |
| Gradle Wrapper + SHA-256 | Gradle 버전과 다운로드 무결성을 고정한다. |
| pnpm-lock.yaml | 같은 소스에서 같은 의존성 조합을 설치한다. |
| Flyway V1~V10 | 테이블 변경을 코드처럼 순서대로 추적한다. 적용된 파일을 고치지 말고 다음 V11 파일을 추가한다. |
| `ddl-auto: validate` | JPA가 테이블을 임의로 수정하지 않고 Entity와 DB 불일치를 발견하면 시작을 멈춘다. |
| 포지션의 `@Enumerated(STRING)` + `@JdbcTypeCode(VARCHAR)` | Java enum 이름을 Flyway의 `VARCHAR(2)` 열에 저장하도록 타입을 명시한다. DB의 CHECK 제약으로 허용한 포지션도 제한한다. |
| `open-in-view: false` | 화면 응답을 만드는 과정에서 예기치 않은 추가 DB 조회가 일어나지 않게 한다. 조회·DTO 변환은 서비스 트랜잭션 안에서 끝낸다. |
| `@Transactional(readOnly = true)` | 읽기 용도의 트랜잭션임을 명시한다. DB 권한을 읽기 전용으로 바꾸는 보안 기능은 아니다. |
| `@Version` | 조회 당시 version과 DB version을 비교하고 동시 저장도 감지한다. 충돌은 409로 응답해 다른 운영진의 변경을 덮어쓰지 않는다. |
| 등번호·가입일의 null 허용 | 모르는 값을 0번이나 오늘 날짜로 바꾸지 않는다. |
| Jackson의 소수→정수 변환 금지와 숫자 enum 거부 | 등번호 1.5를 1로 잘라 저장하거나 숫자를 포지션 순서로 해석하지 않는다. 잘못된 입력은 400으로 거부한다. |
| 선수 ID 순서 + 페이지 최대 100건 | 조회 순서를 일정하게 하고 요청당 반환 크기를 제한한다. |
| 127.0.0.1 바인딩 | 초기 개발용 서비스의 접근 범위를 내 컴퓨터로 정한다. |

## 인증과 변경 기능

현재는 `accounts`에 저장한 계정으로 세션 로그인·로그아웃을 제공합니다. 선수 목록은 ADMIN 또는 MEMBER로 로그인해야 조회할 수 있습니다. 비밀번호는 BCrypt(cost 12) 해시로 저장하며, CSRF 보호와 로그인 시 세션 ID 교체를 사용합니다. 세션 쿠키는 HttpOnly·SameSite=Lax이고 유휴 만료 시간은 30분입니다. HTTPS 배포 시 `SESSION_COOKIE_SECURE=true`를 설정합니다.

로그인 요청의 흐름은 `LoginForm → Spring Security 필터 → AccountUserDetailsService → AccountRepository → accounts`입니다. 비밀번호 확인·세션 저장·로그아웃은 직접 Controller에서 구현하지 않고 Spring Security에 맡깁니다. AuthController는 CSRF 토큰과 현재 로그인 정보만 응답합니다. 이 서비스는 같은 출처의 웹 화면이므로 JWT 저장·갱신을 추가하기보다 서버 세션으로 시작합니다.

로컬 초기 관리자 정보는 Git에서 제외한 `.local/admin-bootstrap.json`에서 실행 스크립트가 환경변수로 전달합니다. AdminBootstrap은 계정 테이블이 비어 있을 때만 계정을 생성합니다. 회원 계정 발급과 비밀번호 변경·복구는 아직 없습니다. 배포 전에는 로그인 시도 제한과 계정 운영 절차도 완성해야 합니다.

선수 저장은 `PlayerEditor → players/api.ts → SecurityConfig → PlayerController → PlayerCommandService → PlayerRepository → MySQL` 순서입니다. 화면에서 운영진에게만 버튼을 보여 주고, 서버에서도 ADMIN 권한과 CSRF 토큰을 검사합니다. 버튼을 숨기는 것만으로 권한을 보호하지 않습니다.

Controller의 요청 DTO는 형식·필수 값을 검사하고, Entity는 이름·등번호·날짜 범위를 지킵니다. QueryService는 읽기 전용 트랜잭션, CommandService는 쓰기 트랜잭션을 사용합니다. 수정은 트랜잭션에서 조회한 Entity를 변경하는 JPA dirty checking을 사용하므로 별도 UPDATE SQL이나 save 재호출이 필요하지 않습니다. 응답 전에 flush하여 실제 UPDATE와 version 증가를 확인합니다.

화면을 열어 둔 동안 다른 운영진이 저장했다면 요청 version 비교에서 409가 발생합니다. 두 요청이 같은 시점에 조회한 경우에도 UPDATE의 version 조건으로 JPA가 충돌을 감지합니다. 화면은 초안을 유지하고 명시적인 최신 정보 불러오기를 제공합니다. 이 흐름은 낙관적 잠금의 학습 예제이기도 합니다.

## 데이터가 늘어날 때 지킬 모델

선호 순위는 고정된 세 지망 요구에 맞춰 `players.first_choice/second_choice/third_choice`에 저장했습니다. 신규 등록과 수정에서는 1지망이 필수지만, 기존 선수의 선호를 임의로 추정하지 않도록 DB 컬럼은 NULL을 허용합니다. 순서·중복·코드 제약은 Entity와 DB에도 적용합니다. 가중치는 향후 편성 정책이며 선수별 고정 속성으로 저장하지 않습니다.

엑셀 파일은 서버의 Apache POI 5.5.1로 읽습니다. 프론트에 별도 Excel 파서를 두지 않아 UI 입력과 Excel 입력이 같은 `BulkPlayerService`의 검증을 거칩니다. `/import/preview`는 파일 내용을 문자열 행으로 변환하고 원본 행 번호와 오류를 반환하며 DB에 저장하지 않습니다. 화면에서 수정한 뒤 `/bulk/preview`로 다시 검사하고 `/bulk`에서 모든 행을 재검증·트랜잭션 저장합니다. 파일 크기·행 수·압축 해제 크기를 제한하고 수식과 매크로는 처리하지 않습니다. 실제 파일을 서버에 보관하는 기능은 없습니다.

선수 1명과 200명의 등록 모두 `Player`의 기본 값·선호 순위 규칙을 지킵니다. 일괄 입력에 오류가 있는 행만 건너뛰면 사용자가 누락을 놓칠 수 있어 이번 단계는 전체 성공/전체 취소로 정했습니다. 동명이인은 가능하므로 이름 일치가 있으면 경고하고 자동으로 병합하지 않습니다. 반복 업로드의 서버측 멱등성 저장은 아직 없으며, 화면은 연타와 저장 결과가 불확실한 요청의 재전송을 제한합니다.

- 선수와 로그인 계정은 별개입니다. 계정이 없는 선수도 명단에 존재할 수 있습니다.
- 인원 부족 시 초청하는 외부 용병은 실제 참가자로 다루며, 이름은 있고 등번호는 없는 경우를 허용해야 합니다. 현재 등번호는 NULL을 허용합니다. 용병의 등록 방식, 정회원과의 구분, 기록·통계·자동 편성 반영 정책은 추후 논의하며 아직 데이터 모델을 확정하지 않습니다.
- 모임 날짜별 출석과 실제 출전 쿼터는 별개입니다.
- 대표 포지션과 선호 1·2·3지망은 별도로 저장합니다. 마지막 확장 단계의 참석 투표 결과, 당일 실제 출석, 예정 라인업, 실제 출전 기록도 각각 구분합니다.
- 초기 자동 편성은 11인제 4-1-2-3으로 고정합니다. 선호 포지션은 LB, CB, RB, CDM, CM, LW, ST, RW, GK만 허용합니다. 쿼터마다 CB·CM은 각각 2명, 나머지는 각각 1명으로 총 11자리를 구성하며, 같은 포지션의 두 자리는 별도 배치 자리로 구분합니다. 다른 포메이션은 이후 별도 확장으로 검토합니다.
- 쿼터별 자동 편성은 출전 가능 범위와 포지션 조건을 지키면서 총 출전 시간 차이를 최소화하고 선호 포지션을 반영하는 방향으로 설계합니다. 운영진의 수정·확정 후 예정 출전량을 다시 계산하며, 계획을 실제 기록으로 자동 확정하지 않습니다. 세부 범위는 [로드맵](roadmap.md)의 5-1단계를 따릅니다.
- 한 모임에 여러 경기와 상대 팀이 있을 수 있습니다.
- 경기당 4쿼터로 시작하며 쿼터 길이와 교체 시각은 저장하지 않습니다. 같은 자리의 선발·교체는 각각 0.5쿼터, 교체 없는 선발은 1쿼터입니다.
- 실제 출전 명단과 개인 기록을 보존합니다. 마지막 단계의 프로 비교는 4쿼터=1경기를 후보로만 기록하며 환산 기준은 아직 결정하지 않았습니다. 비교 기능의 구현 시점과 세부 범위는 [로드맵](roadmap.md)의 5단계를 따릅니다.
- 득점 기록이 없는 것과 득점 0이 확인된 것을 구분합니다.
- 몸값 계산식을 도입할 때는 계산식 버전과 산출 근거를 이력에 함께 남깁니다.

위 항목 중 경기·투표·출석·쿼터별 직접 입력과 1:1 교체는 아래 단계에서 구현했습니다. 자동 편성·모임 묶음·기록 확정·몸값 등 나머지는 이후 설계 기준입니다.

## 경기 중심의 기록 구조

사용자는 별도 모임 등록보다 매주의 경기 기록을 먼저 원하므로 `match` 기능에 날짜·상대·장소와 투표·실제 출석·4쿼터 기록을 모았습니다. 화면 요청은 `MatchEditor → matches/api.ts → MatchController → MatchService → MatchRepository` 순서로 이동합니다. 조회는 ADMIN/MEMBER, 저장은 ADMIN과 CSRF 검사로 보호합니다.

DB는 경기 기본 정보, 참가자별 투표·출석, 쿼터 번호, 쿼터별 출전 자리·선발/교체·득점·도움으로 나눕니다. 투표의 참석 예정은 출석의 참석으로 자동 확정하지 않습니다. 같은 선수가 참석하고도 한 쿼터도 뛰지 않은 경우를 보존하고, 미래의 출석 순위와 득점 순위를 각자의 원본에서 계산하기 위한 구조입니다.

초기에는 한 경기의 참가자 최대 200명, 배치 최대 88개(4쿼터 × 11자리 × 선발/교체)로 범위가 작고 함께 수정하므로 JPA `@ElementCollection` 값 객체로 관리합니다. 저장 전에 참가자 존재 여부와 출석·자리·선수 중복 등 규칙을 검사하고 한 트랜잭션으로 모두 저장합니다. DB도 선수/경기 FK, 같은 쿼터의 선수 UNIQUE, 코드와 숫자 CHECK를 적용합니다. 참가자 상태와 출전 기록 사이의 규칙은 도메인에서 검사합니다.

`MatchRecord`의 `@Version`은 하위 컬렉션만 수정해도 증가합니다. 전체 경기 단위의 충돌 감지를 통해 서로 다른 운영진이 출석과 라인업을 각자 저장하면서 이전 값으로 덮어쓰는 일을 막습니다. 409 또는 저장 결과 불명 시 화면은 초안을 유지하고 재전송을 멈춥니다. 신규 생성의 서버 멱등성 처리는 추후 범위입니다.

현재 4쿼터와 4-1-2-3을 고정합니다. 교체는 같은 자리의 선발 1명과 교체 1명이며 각각 0.5쿼터로 계산합니다. 재투입·같은 쿼터의 포지션 이동은 지원하지 않습니다. 출전량은 원본에서 계산하므로 별도 합계 컬럼이 원본과 어긋날 수 없습니다. V5가 기존 배치를 선발로 보존하고 길이 컬럼을 제거합니다. 미배치 자리는 미기록, 득점·도움 초기값은 0입니다. 기록 확정과 미확인 득점 구분은 후속 단계입니다.

경기 엑셀은 `MatchWorkbookImport → MatchImportController → MatchWorkbookService`에서 읽어 등록된 선수 ID에 연결합니다. Apache POI로 값을 검사하고 행별 오류를 보여 주며 수식은 실행하지 않습니다. 미리보기는 쓰기가 없고, 반영 시 4쿼터 초안 전체만 교체합니다. 투표·실제 출석·코멘트는 유지하며 새 참가자는 미확인 상태여서 출석을 확인해야 저장됩니다. 최종 저장은 기존 경기 저장 흐름으로 다시 검증하여 UI·엑셀의 규칙을 일치시킵니다.

## 테스트의 경계

선수의 `birth_year`와 `club_role`은 V6에서 선택 컬럼으로 추가했습니다. 나이 자체는 저장하면 해마다 값이 낡기 때문에 `players/age.ts`에서 기준 연도 − 생년으로 계산합니다. 선수단은 한국의 현재 연도, 경기 명단은 해당 경기 연도를 사용합니다. 생일은 사용하지 않으며 연도 경계와 20대→30대 경계를 Node 테스트로 확인합니다. 팀 직책은 인증 권한과 연결하지 않습니다.

포지션 미확인 `UN`은 선호 포지션이 없다는 사실을 명시하는 값입니다. 임의의 포지션을 배정하지 않고 정상 활동 선수로 보존합니다. UN이면 지망 세 칸은 NULL이고, 나머지 포지션은 기존 1지망 필수 규칙을 유지합니다. UI·API·일괄 등록·엑셀에 같은 규칙을 적용합니다. 실제 선수 정보는 테스트 fixture나 Flyway에 넣지 않습니다.

`PlayerTest`는 선수 입력과 변경 규칙, `PlayerCommandServiceTest`는 오래된 버전 거부와 활동 선수만 수정하는 규칙을 검증합니다. `PlayerControllerTest`는 입력 검증·운영진 권한·CSRF·충돌 응답을 확인합니다. `PlayerIntegrationTest`는 실제 MySQL에서 Flyway 테이블 생성, JPA 매핑, 페이지 구분, 저장·수정·버전 충돌을 함께 확인하도록 작성했습니다. 실제 실행 여부는 검증 기록에 구분합니다.

배포나 CI 정의가 있는 것과 실제로 배포·CI 실행이 성공한 것은 구분해서 기록합니다. 성능 실험도 실제 회원 사용량과 합성 데이터의 부하 테스트를 구분합니다.

## 선수단 조회와 번호 제약

카드와 표는 같은 조회 응답을 사용합니다. 화면은 기본 등번호 오름차순·20명을 요청하고, `PlayerQueryService`가 전체 활동 선수를 정렬한 뒤 페이지를 나눕니다. 한 페이지를 브라우저에서만 정렬하면 페이지 사이 순서가 틀리므로 서버에서 처리합니다. 생년·번호 NULL은 항상 뒤로, 동률은 ID로 순서를 고정합니다. 선호 포지션순은 SQL CASE로 1지망을 GK/수비/미드/공격 그룹에 매핑합니다. 방향은 그룹에만 적용하고 그룹 내 번호 오름차순·번호 NULL 마지막·ID 순서를 유지하며, 1지망 NULL 그룹은 항상 끝에 둡니다. 정렬용 값을 DB에 중복 저장하지 않습니다. 생년 입력과 목록 선택은 같은 React 상태를 사용합니다. 선수단 링크는 `SquadSection`의 이동 함수를 호출하여 편집 중 경고와 처리 중 이동 방지를 적용합니다.

V7은 팀 직책의 다섯 값을 제한합니다. V8은 활동 선수 번호만 노출하는 생성 컬럼에 UNIQUE를 걸어 동시 요청도 막습니다. API 사전 조회는 친절한 안내를 위한 것이며 최종 보장은 DB가 합니다. V9에서 등번호 범위를 1~99로 좁혔습니다. 등번호는 바뀌고 없는 선수도 있으므로 PK와 경기 외래 키는 고정 ID를 유지합니다.

## 경기 전 계획과 경기 후 기록

`AttendeePicker`는 이름·등번호 검색과 체크로 참석 투표를 입력합니다. 실제 출석은 별도이며 체크 해제도 불참으로 추측하지 않습니다. `MatchPlanner`의 드래그와 클릭 배치는 같은 `placeInPlan` 함수를 사용하여 자리 교환·한 쿼터 중복 금지·선발 없는 교체 금지를 일관되게 처리합니다. 총 계획 쿼터는 교체 두 명 각각 0.5, 단독 선발 1로 계산합니다. `AutomaticLineup`은 별도 계산 API의 결과를 계획 초안에 반영하며 자세한 정책은 [자동 편성 설명](automatic-lineup.md)을 따릅니다.

V10 `match_planned_lineups`에는 계획만 저장하고, 득점·도움과 실제 출전량은 `match_appearances`에서만 집계합니다. 투표·계획·실제 기록은 한 경기 트랜잭션과 version으로 함께 저장합니다. 계획에는 참석 예정자만 넣을 수 있습니다. 03의 ‘02 계획대로 참석·출전 기록 저장’은 계획을 실제 배치로 복사하고 참석 예정자 중 미확인을 참석으로 바꾼 전체 초안을 기존 저장 API로 보냅니다. 응답 성공 후에만 화면을 갱신합니다. 지각·불참은 유지하고, 계획에 실제 불참자가 있거나 기존 실제 출전이 하나라도 있으면 일괄 복사를 막습니다. 이후 변경은 직접 수정·저장합니다.

V11은 `players.player_type`으로 MEMBER/GUEST를 구분합니다. 실제 참가자인 용병에게도 안정적인 선수 ID를 부여해 경기·자동 편성·재참가에 같은 FK를 사용합니다. 임의의 이름이나 등번호를 만드는 더미 데이터 방식은 사용하지 않습니다. 정회원 목록은 MEMBER만, 별도 운영진용 용병 API는 GUEST만 조회합니다. 프로필 등록과 경기 저장은 별도 동작이며 등록된 프로필은 경기 초안을 취소해도 재사용할 수 있습니다.

V12는 경기 전체 스코어를 `score_for/score_against`에 선택 값으로 보관합니다. 득점자 미기록·상대 자책골 때문에 개인 득점 합계로 강제 계산하지 않으며 차이는 화면에서 안내합니다. 목록은 먼저 경기 10개 페이지를 읽고 해당 ID들의 실제 득점자를 한 쿼리로 집계합니다. 등번호순 최대 3명과 전체 득점자 수를 응답하여 상세 화면을 경기마다 추가 요청하지 않습니다.

시작 시간은 API에서 필수·30분 단위로 검증하고, 표시용 종료 시간은 프론트에서 2시간을 더해 계산합니다. 기존 시간 NULL·비정규 시간을 보존하기 위해 DB를 일괄 변경하지 않으며 다음 수정 때 새 규칙을 요구합니다. 01~04 패널은 숨김 방식으로 전환해 쿼터 선택·용병 입력·엑셀 미리보기 같은 내부 상태도 유지하고, 경기 초안은 MatchEditor 한 곳에서 관리합니다. 어느 단계에서 저장하든 같은 전체 저장 API와 version을 사용합니다.
