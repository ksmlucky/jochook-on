# 팀 생성·팀 코드 접속 스토리보드

작성일·구현 승인일: 2026-10-14. 기존 V16 팀 접속 화면과 V17 팀 비밀번호의 검증 이력은 [검증 기록](verification.md)을 따른다. 아래 현재 흐름은 감독·코치 역할 분리를 반영한 기준이며, 신규 V18 기능의 검증 완료를 뜻하지 않는다. 감독의 코치 관리 상세는 [추가 스토리보드](team-staff-permissions.md)의 TS-S01~S04를 따른다. `outputs/`의 독립 HTML 시안은 구현 전 검토 자료이며 실제 서비스가 아니다.

## 1. 전체 흐름과 공통 표시

```text
TA-S01 접속 홈 ─ 코드 성공 ───────────────→ TA-S08 회원 대시보드
    └ 운영진 로그인 → TA-S02
         ├ 서비스 관리자 → TA-S03 팀 관리 → TA-S04 팀 생성·최초 감독 지정
         │                                      └ 개인 전달한 초대 → TA-S05 활성화
         └ 활성 감독·코치 → 내 팀 기록 / TA-S06 코드 관리 → TA-S07 발급 결과
              └ 감독만 → TS-S02 코치 관리 → 임명 / 초대 / 조회로 전환

팀 전환: TA-S03 또는 TA-S08 → TA-S09 전환 확인 → 허용한 새 팀
접근 만료/거부: 각 화면 → TA-S10 상태 안내 → TA-S01 또는 TA-S02
```

상단에는 **조축ON**과 현재 팀을 구분한다. 미접속 상태에서는 특정 팀 명단을 보이지 않는다. 접속한 뒤에는 `조회 전용`, `감독`, `코치`로 권한을 구분한다. 서비스 관리자는 별도 `서비스 관리` 메뉴를 이용한다. 권한 없는 기능은 메뉴에서 숨기고 서버도 거부한다. 선수의 직책이 아닌 로그인 계정의 현재 팀 역할을 사용한다.

한 열의 휴대전화 화면을 기본으로 한다. 주요 버튼은 입력란 아래에 배치하고, 처리 중에는 버튼을 비활성화한다. 일반 저장 성공은 기존의 반투명 자동 종료 알림을 사용한다. **새 코드·초대 링크 원문과 폐기 확인은 자동으로 사라지는 알림에 넣지 않는다.** 오류는 사용자가 조치할 수 있도록 화면에 유지한다.

## TA-S01. 접속 홈

```text
┌─────────────────────────┐
│ 조축ON                  │
│ 우리 팀의 축구 기록     │
│                         │
│ 팀 코드                 │
│ [ 코드를 입력하세요   ] │
│ 팀 비밀번호             │
│ [ 숫자 6자리          ] │
│ 운영진이 준 두 값으로   │
│ 우리 팀을 조회할 수 있어요│
│ [ 우리 팀 들어가기    ] │
│                         │
│ 운영진 로그인 →         │
└─────────────────────────┘
```

- 코드와 숫자 6자리 팀 비밀번호를 한 화면에서 입력한다. 붙여넣기를 지원하고 앞 0을 보존한다. 팀명·이름·생년·회원 가입은 요구하지 않는다.
- 버튼은 `접속 확인 중…` → 두 값이 모두 유효하면 서버가 확인한 팀의 TA-S08로 이동한다. 어느 값이 틀렸는지 공개하지 않고 두 값을 함께 확인하도록 안내한다. 상세는 [팀 비밀번호 화면](team-code-password.md)을 따른다.
- 기존 조회 세션이면 해당 팀으로 이어서 접속하고 `다른 팀 들어가기`에서 전환한다. 다른 코드 확인이 실패해도 기존 팀 세션을 임의로 변경하지 않는다.
- 조회 제한이면 대기시간, 통신 실패면 `연결하지 못했습니다. 잠시 후 다시 시도해 주세요.`를 표시한다. 입력 코드는 URL이나 영구 저장에 남기지 않는다.
- 연결: TA-R01·R07·R09·R11 / TA-A01·A10·A13·A15. 코드 형태·세션·실패 제한은 승인된 P06·P09·P11 정책.

## TA-S02. 운영진 로그인

```text
┌─────────────────────────┐
│ 조축ON · 운영진 로그인 │
│ 아이디 [              ] │
│ 비밀번호 [            ] │
│ [ 로그인              ] │
│ 계정이 없으면 초대해 준 │
│ 서비스 관리자에게 문의 │
│ ← 팀 코드로 들어가기    │
└─────────────────────────┘
```

- 기존 아이디·비밀번호 방식과 CSRF·세션 교체를 유지한다. 서비스 관리자는 별도 공개 가입/관리자 체크박스 없이 자신의 지정된 계정으로 로그인한다.
- 운영진 소속 팀이 하나면 해당 팀 기록으로, 여러 개면 TA-S03의 내 팀 목록으로 이동한다. 서비스 관리 권한만 있으면 서비스 팀 관리로 이동한다.
- 활성 소속이 없으면 `활성화된 운영 팀이 없습니다. 초대 상태를 확인하거나 서비스 관리자에게 문의해 주세요.`를 표시한다. 무소속 계정에 팀을 자동 생성하지 않는다.
- 호환 대상인 기존 MEMBER 계정은 자신의 기존 팀 조회 화면으로 이동하고 수정 권한은 부여하지 않는다.
- 로그인 실패는 `아이디 또는 비밀번호를 확인해 주세요.`로 유지한다. 공개 회원 가입과 이메일 비밀번호 복구 버튼은 이번 범위에서 제공하지 않는다.
- 연결: TA-R01·R04·R11 / TA-A02·A06·A07·A15.

## TA-S03. 서비스 팀 관리 / 내 팀 목록

```text
┌─────────────────────────┐
│ 조축ON · 서비스 관리   │
│ 팀 관리    [ + 팀 생성 ]│
│ [ 팀명/구분 설명 검색 ] │
│                         │
│ 예시 FC · 서울 동부     │
│ 운영진 설정 대기        │
│ [ 운영진 지정 관리    ] │
│                         │
│ 예시 풋볼 · 경기 남부   │
│ 운영 중                 │
│ [ 운영진 지정 관리    ] │
└─────────────────────────┘
```

- 예시 팀은 설명용 가상 이름이다. 서비스 관리 목록은 팀명·구분 설명·운영 상태를 표시하고, 지정된 계정과 초대 상태는 `운영진 지정 관리` 상세에서 확인한다. 선수 명단·경기 내용을 펼치지 않는다.
- 서비스의 운영진 지정 관리는 현재 계정의 감독/코치 역할과 활성/초대 대기/만료 상태를 표시한다. 서비스 관리자는 감독/코치를 지정하고 초대·소속을 관리한다. 마지막 활성 감독은 다른 감독이 활성화되기 전 해제하거나 코치로 변경하지 못한다.
- 본인 운영진 소속도 있는 팀에만 `내 팀으로 이동`을 제공한다. 서비스 관리 역할만으로 코드 관리나 기록 수정 버튼을 표시하지 않는다.
- 팀 운영진의 `내 팀 목록`은 **자신의 활성 소속만** 보여 주고 `팀 생성`·다른 팀 검색·서비스의 감독 지정 관리는 제공하지 않는다. 감독에게는 별도 `코치 관리`를 제공한다. 전환 시 TA-S09를 거친다.
- 목록이 비었으면 역할에 따라 `아직 만든 팀이 없습니다. 팀을 만들고 운영진을 지정하세요.` 또는 `운영 가능한 팀이 없습니다.`를 표시한다.
- 연결: TA-R02·R03·R04·R13 / TA-A02·A04·A06·A07·A17.

## TA-S04. 팀 생성·최초 감독 지정

```text
┌─────────────────────────┐
│ ← 팀 관리   새 팀 만들기│
│ 팀명 * [              ] │
│ 지역/구분 설명 [       ] │
│                         │
│ 최초 감독 지정 *        │
│ ( ) 기존 계정 지정      │
│ (●) 새 감독 초대        │
│ 지정 대상 표시명 [     ]│
│ 24시간 활성화 링크 발급 │
│                         │
│ [ 팀 생성 · 초대 발급 ]│
└─────────────────────────┘
```

- `*`는 필수. 팀명 2~40자, 구분 설명 선택은 승인된 P01 정책이다. 동일 팀명을 금지하지 않으며 팀명만으로 기존 팀에 합치지 않는다.
- 기존 계정 지정은 정확한 로그인 ID를 입력해 일치하는 계정만 확인하고 서비스 관리자가 지정할 팀·대상을 최종 확인한다. 저장하면 DIRECTOR 소속을 직접 지정하며 대상자는 기존 계정으로 로그인해 사용한다. 이 경로에는 별도 초대 수락 링크가 없다. 불특정 계정 검색 결과를 공개하지 않는다.
- 신규 초대의 표시명은 서비스 관리자가 구분하는 임시 메모이며 회원 프로필·본인 인증 수단이 아니다. 공개 샘플에 실제 이름을 넣지 않는다. 활성화 링크는 팀과 초대 건에 묶고 복사 후 지정 대상에게 개인 전달한다. 링크 소지자가 활성화할 수 있으므로 결과 화면에 `지정한 운영진에게만 개인적으로 전달해 주세요.`를 안내한다.
- 새 감독 초대를 선택하면 생성 성공 후 설정 대기와 `초대 링크 복사`를 보여 준다. 기존 계정에 지정하면 버튼과 결과에 감독 지정임을 명시한다. 새 팀의 첫 초대 역할은 DIRECTOR로 고정한다.
- 동일 요청을 여러 번 보내도 팀·초대를 중복 생성하지 않는다. 응답 유실은 `생성 결과를 확인하지 못했습니다. 팀 목록에서 상태를 확인해 주세요.`와 `팀 목록 확인`을 제공한다. 원문 링크를 놓쳤으면 초대 상태를 확인하고 재발급한다.
- 입력 오류는 해당 항목 아래, 처리 실패는 상단에 표시하고 입력을 유지한다. 생성 성공 전에는 완료 화면으로 이동하지 않는다.
- 연결: TA-R02·R03·R11·R13 / TA-A02·A03·A04·A05·A17. 활성화 기간·개인 전달 방식은 승인된 P03 정책.

## TA-S05. 운영진 활성화

```text
┌─────────────────────────┐
│ 조축ON · 운영진 초대   │
│ 예시 FC의 운영진으로   │
│ 초대받았습니다.         │
│                         │
│ 새 계정 만들기          │
│ 아이디 * [            ]│
│ 비밀번호 * [          ]│
│ 비밀번호 확인 * [     ]│
│ [ 계정 설정 · 참여    ]│
│ 기존 계정으로 수락 →    │
└─────────────────────────┘
```

- 유효 링크 확인 후 초대한 팀과 `감독` 또는 `코치` 역할을 보여 준다. 링크 검증 전에는 팀·대상 정보를 표시하지 않는다. 수락자가 역할을 직접 고르는 드롭다운이나 서비스 관리자 권한 선택은 없다.
- 새 계정 아이디는 영문 소문자로 시작하는 3~40자, 비밀번호는 12자 이상·UTF-8 72바이트 이내다. 대상자가 직접 설정하고 서비스 관리자가 비밀번호를 대신 정해 전달하지 않는다. 활성화 링크는 43자 일회용 토큰을 사용하며 화면이 읽은 뒤 주소에서 지우고 메모리에서만 유지한다.
- **신규 초대에서 이미 가진 계정을 사용하려는 경우** 개인 로그인 후 해당 초대를 수락한다. 입력한 ID가 이미 있으면 기존 계정 로그인을 안내하고 덮어쓰지 않는다. 특정 기존 계정에 묶인 초대만 다른 계정의 수락을 거부할 수 있다. 일반 신규 초대의 표시명만으로 실명을 확인한 것으로 처리하지 않는다.
- 성공하면 초대를 소비하고 지정된 역할의 팀 소속을 활성화한 뒤 해당 팀으로 이동한다. 같은 링크 재사용은 소속을 중복 생성하지 않는다. 기존 활성 감독이 코치 초대를 수락해도 감독 권한을 낮추지 않는다.
- 발급자가 현재 해당 역할을 초대할 권한을 잃었다면 남은 기간이 있어도 링크를 거부한다. 현 감독/서비스 관리자에게 재발급을 요청하도록 안내한다.
- 만료·취소·이미 사용한 링크는 TA-S10에서 `초대 링크를 사용할 수 없습니다. 서비스 관리자에게 새 초대를 요청해 주세요.`를 표시한다. 회원 코드를 새로 입력해도 이 초대 권한을 얻을 수 없다.
- 연결: TA-R03·R11·R13 / TA-A04·A05·A17. 일회용·발급 후 24시간은 승인된 P03·P04 정책.

## TA-S06. 팀 코드 관리

```text
┌─────────────────────────┐
│ 조축ON   예시 FC · 운영진│
│ 회원 조회 코드 관리     │
│ 상태: 사용 중           │
│ 만료: 발급 후 90일      │
│ 원문은 다시 볼 수 없어요│
│                         │
│ [ 새 코드로 재발급    ]│
│ [ 현재 코드 폐기     ]│
│ 이 코드는 조회 전용입니다│
└─────────────────────────┘
```

- 미발급·폐기·만료 상태이면 `조회 코드 발급`을 제공한다. 사용 중이면 상태·발급일·만료일을 표시하며 원문은 표시하지 않는다. 최근 20건의 발급·재발급·폐기 이력에서 작업 종류·담당 계정·코드 버전·처리 시각·만료일을 확인한다. 이력에도 코드 원문이나 해시를 표시하지 않는다.
- 재발급 확인: `새 코드를 발급하면 이전 코드로 접속한 회원은 다시 접속해야 합니다.` / `취소`, `재발급`.
- 폐기 확인: `회원의 코드 접속을 종료합니다. 다시 공유하려면 새 코드를 발급해야 합니다.` / `취소`, `폐기`.
- 발급/재발급 성공은 TA-S07로 이동한다. 폐기는 상태를 바꾸고 자동 종료 성공 알림을 표시한다. 실패하면 현재 상태를 유지하고 재조회·재시도를 안내한다.
- 다른 운영진이 동시에 변경했으면 `코드 상태가 변경되었습니다. 최신 상태를 확인해 주세요.`를 표시한다. 오래된 화면에서 두 번 성공한 것처럼 보이지 않게 한다.
- 운영진 개인 로그아웃을 일으키지 않으며 코드 조회 세션만 종료한다. 해당 팀 소속이 없는 서비스 관리자도 사용할 수 없다.
- 연결: TA-R05·R06·R11·R12 / TA-A08·A09·A15·A16.

## TA-S07. 코드 발급 결과 — 원문 1회 표시

```text
┌─────────────────────────┐
│ 예시 FC · 발급 완료    │
│                         │
│ [발급된 코드 표시 영역] │
│ [ 코드 복사           ]│
│                         │
│ 유효기간: 발급 후 90일  │
│ 이 화면을 닫으면 코드를 │
│ 다시 볼 수 없습니다.    │
│ 운영진 권한은 포함 안 됨│
│                         │
│ [ 복사했어요 · 닫기   ]│
└─────────────────────────┘
```

- 실제 코드는 이 문서/시안에 넣지 않는다. 설명용 화면의 코드는 실제 사용 불가한 자리 표시자다.
- 서버의 성공 응답에서 받은 원문만 일시적으로 표시한다. 화면은 자동으로 닫히지 않는다. 복사 성공은 `코드를 복사했습니다.`로 알리고 복사 실패 시 직접 선택할 수 있도록 한다.
- 닫기/뒤로가기/새로고침 시 원문은 재조회하지 않는다. 새로고침 후 TA-S06의 코드 상태를 보여 주며 분실 시 재발급을 안내한다. 운영진이 복사해 직접 팀에 공유하고 앱은 자동 메시지를 보내지 않는다.
- 연결: TA-R05·R12 / TA-A08·A16. 원문 1회 표시는 승인된 P08 정책.

## TA-S08. 회원 대시보드

```text
┌─────────────────────────┐
│ 조축ON                  │
│ 예시 FC      조회 전용  │
│ [ 선수단 ] [ 경기 기록 ]│
│                         │
│ 선수단                  │
│ 기존 카드/표 · 검색·정렬│
│                         │
│ 경기 기록               │
│ 기존 일정·스코어·상세   │
│                         │
│ 다른 팀 들어가기 / 나가기│
└─────────────────────────┘
```

- 현재 선수단·경기 조회 화면을 재사용한다. 이번 단계에서 새로운 시즌 순위·통계 대시보드를 추가하지 않는다.
- 코드로 조회하는 회원에게 선수 등록·수정, 경기 등록·저장, 엑셀, 자동 편성, 코드 관리 버튼을 제공하지 않는다. 이미 저장된 계획·실제 출전·결과는 조회 범위에 포함한다.
- 새 팀의 빈 상태는 `아직 등록된 선수가 없습니다.` / `아직 등록된 경기가 없습니다.`로 안내한다. 다른 팀 기록을 예시처럼 채우지 않는다.
- `나가기`는 조회 세션을 종료하고 TA-S01로 이동한다. 다른 팀 코드는 TA-S09 안내 후 확인하며, 유효 코드 확인 전 기존 팀을 바꾸지 않는다.
- 연결: TA-R01·R07·R08 / TA-A01·A10·A11·A12.

## TA-S09. 팀·접속 방식 전환과 미저장 안내

```text
┌─────────────────────────┐
│ 저장하지 않은 내용이 있어요│
│ 팀을 바꾸면 현재 작성한 │
│ 내용을 이어갈 수 없습니다│
│                         │
│ [ 계속 작성           ]│
│ [ 저장 안 하고 전환   ]│
└─────────────────────────┘
```

- 운영진이 팀을 바꿀 때 현재 팀·다음 팀을 구분해 보여 준다. 미저장 선수/경기/코드 관리 입력이 있으면 안내하고 기본 행동은 계속 작성이다. 저장 중에는 전환 버튼을 잠시 막는다.
- 전환을 취소하면 초안 유지. 전환하면 이전 팀 초안·목록·상세·캐시와 진행 중 조회 응답을 정리하고 새 팀 데이터를 요청한다. 이전 팀 초안을 새 팀에 자동 저장하지 않는다.
- 다른 브라우저 탭에서 현재 팀이나 접속 방식이 바뀌면 기존 탭은 내용을 새 팀 것으로 간주하지 않고 재확인을 안내한다. 저장 요청에 기대하는 팀 ID를 함께 보내며, 서버는 요청의 팀과 현재 세션·소속 권한이 다르면 저장을 거부한다. ID를 보내는 것 자체가 권한 증명은 아니다.
- 운영진에서 회원 코드 접속으로 바꾸면 확인 후 로그아웃하고 TA-S01로 이동한다. 회원에서 운영진 로그인은 새 인증 성공 시 조회 세션을 교체하며 권한을 합치지 않는다.
- 연결: TA-R04·R09 / TA-A06·A13. 한 세션 한 팀/접속 방식은 승인된 P12 정책.

## 3. 화면 검토 체크리스트

- 회원은 홈에서 코드와 팀 비밀번호를 함께 입력해 자신의 팀 조회로 갈 수 있는가?
- 서비스 관리자의 팀 생성·감독 지정, 감독의 코치 관리, 감독·코치의 코드 관리가 구분되는가?
- 새 팀 생성 후 운영진 활성화·코드 발급·회원 접속까지 막히는 단계가 없는가?
- 재발급/폐기가 이미 접속한 회원에게 미치는 영향과 원문 재조회 불가가 작업 전에 보이는가?
- 휴대전화에서도 팀명·접속 역할·주요 버튼·오류를 읽고 누를 수 있는가?
- 실제 연결한 앱 화면과 API가 없는 과거 HTML 시안을 구분해 표시했는가?

이 체크리스트는 승인된 화면 기준의 검토용이다. 실제 앱의 코드 조회·운영진 로그인·팀 생성·초대·팀 전환·미저장 보호·코드 이력 흐름을 확인했고 390px 폭 팀 목록의 가로 넘침이 없음을 검증했다. API·MySQL·브라우저별 확인 범위는 검증 기록을 따른다.

## 4. 로컬 검토 산출물과 확인 결과

### 실제 앱 최종 확인 — 2026-10-14

- 코드 접속의 조회 전용 화면, 운영진 로그인, 서비스 관리자의 기존 계정 지정 방식 팀 생성, 초대 발급 원문 닫기와 기존 계정 초대 수락을 확인했다. 초대 링크를 읽은 뒤 URL fragment에서 원문이 제거됐다.
- 두 팀 소속 선택, 미저장 입력 유지·폐기, 다른 탭에서 팀을 전환했을 때 이전 초안 저장 차단을 확인했다. 이전 팀 데이터를 새 팀으로 자동 저장하지 않았다.
- 코드의 4-4-4 형식·원문 1회 표시·닫기 후 마스킹과 코드 변경 이력 갱신을 확인했다. 390px 모바일 폭의 팀 목록에서 가로 넘침이 없었다.
- 가상 팀은 격리 QA DB에서만 사용했다. 실제 로컬 앱은 V16까지 적용했고 HANA FC만 유지하며 조회 코드는 아직 미발급이다. 공개 서버 배포·실제 아이폰 외부 접속은 후속 작업이다.

### 이전 정적 시안 검토 기록

- 아래는 구현 승인 전 정적 시안 검토 기록이다. 승인된 정책은 이 문서와 요구사항 정의서를 따르며, 시안 확인을 실제 앱 기능 검증으로 간주하지 않는다.
- `outputs/team-access-storyboard.html`은 이 문서의 화면 10개를 눌러 보는 독립 HTML 시안이다. 파일을 브라우저로 열 수 있으며, `outputs/`는 Git 제외 경로다. 가상 팀·계정·코드만 사용하고 실제 API 요청이나 DB 저장은 없다.
- 2026-10-14 브라우저에서 화면 10개 이동, 회원 조회, 기존 계정 직접 지정, 신규 초대 → 활성화 → 코드 관리, 재발급 확인 → 원문 표시/닫기 → 이전 회원 세션 안내를 확인했다. 확인한 시안에서 JavaScript 콘솔 오류는 없었다.
- 문서의 요구사항 13개·인수 기준 17개·화면 10개 연결과 백엔드 관점의 권한·데이터 분리 조건을 검토했다. 이 과거 시안 확인 시점에는 앱 단위/API·MySQL 통합 테스트를 실행하지 않았으며 시안 동작 확인을 실제 기능 테스트 통과로 간주하지 않는다.
- 현재 실제 구현은 `features/auth`의 코드 입력·로그인·초대 활성화, `features/teams`의 서비스 팀 관리·내 팀·코드 관리와 기존 선수·경기 화면을 연결한다. 백엔드 계약은 [팀 접속 API](team-access-api.md), 최종 QA 상태는 [검증 기록](verification.md)을 따른다.
