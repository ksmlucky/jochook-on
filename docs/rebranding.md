# 조축ON 이름·팀 표시 분리

작성일: 2026-10-14. 이번 기능의 기획 명세와 간단한 스토리보드다. 구현·실행 검증 결과는 [검증 기록](verification.md)에 별도로 남긴다.

## 문제와 목적

기존 제품명이 한 팀의 이름과 결합돼 있어 서비스를 다른 조기축구팀까지 확장할 때 제품과 소속 팀을 구분하기 어려웠다. 서비스는 **조축ON**, 현재 소속 팀은 **HANA FC**로 구분한다. 기존 선수·경기 기록을 그대로 사용하면서 표시명과 개발용 명칭을 정리한다.

## 요구사항과 범위

| 구분 | 기준 |
| --- | --- |
| 제품 표시명 | 조축ON |
| 현재 소속 팀명 | HANA FC |
| 영문 코드명 | `jochookOn` |
| 저장소·패키지 slug | `jochook-on` |
| 프론트 패키지 | `@jochook-on/web` |
| Java 기본 패키지·시작 클래스 | `com.jochookon.JochookOnApplication` |
| 로컬 실행기 | `Start-JochookON.cmd`, `Stop-JochookON.cmd`, `Dev-JochookON.cmd` |
| GitHub 주소 | `https://github.com/ksmlucky/jochook-on` — 실제 변경 결과는 검증 기록에서 확인 |

- 로그인·공통 헤더·서비스 설명·브라우저 제목의 제품명은 조축ON으로 표시한다. 소속 팀을 안내하는 곳은 HANA FC로 별도 표시한다.
- 팀 표시가 새로운 팀 선택 기능으로 오해되지 않도록 한다. 선택할 팀이 없는 현재 단계에서는 팀 생성·팀 전환 버튼을 추가하지 않는다.
- 기존 로그인과 선수단·경기 기록의 화면 이동, 저장 규칙, API 경로와 데이터 연결을 유지한다.
- 다운로드 양식의 제품 이름과 코드·문서의 실행 예시는 새 명칭에 맞춘다. 이전 양식의 입력 호환성을 이름 변경만으로 제거하지 않는다.
- 실제 팀 생성, 공유 코드 발급·접속, 팀별 DB 데이터 분리·권한 검사는 다음 기능에서 설계·구현한다. 이번 브랜드 변경을 여러 팀 운영 완료로 표시하지 않는다.

## 스토리보드

```text
브라우저 제목: 조축ON
  ↓
로그인 화면
  제품: 조축ON / 조기축구팀 관리 안내
  기존 계정 입력·로그인·오류 안내
  ↓ 로그인 성공
공통 헤더
  제품: 조축ON
  소속 팀: HANA FC
  선수단 / 경기 기록 / 계정 메뉴
  ├─ 선수단: 기존 조회·등록·수정·엑셀 흐름
  └─ 경기 기록: 기존 01 투표 → 02 계획 → 03 실제 출전 → 04 결과 흐름
  ↓ 로그아웃
조축ON 로그인 화면
```

로그인 오류, 로딩, 빈 명단, 저장 실패·성공 알림의 동작을 유지한다. 좁은 화면에서도 제품명과 팀명이 겹치거나 같은 이름으로 보이지 않도록 확인한다. 상세 시각 디자인은 기존 파란색 화면을 유지하는 범위에서 조정한다.

## 데이터와 설정 호환성

- 실제 로컬 폴더 경로는 기존 `HANA FC Transfermarkt`다. 폴더 이동과 로컬 데이터 삭제는 이번 범위가 아니다.
- IntelliJ의 로컬 프로젝트 표시명은 `.idea/.name`의 조축ON을 사용한다. 이 IDE 설정은 Git에서 제외하며 Codex에 연결된 폴더 경로를 변경하지 않는다.
- 실제 MySQL DB·사용자 이름과 기존 영구 볼륨을 유지한다. Compose 프로젝트 이름이 바뀌어도 기존 볼륨 이름을 명시해 같은 데이터에 연결한다.
- 새 설정은 `JOCHOOK_ON_*`와 `jochookon.bootstrap.admin.*`를 사용하고, 기존 `HANA_*`·`hana.*` 설정을 호환 입력으로 받는다. 관리자 비밀번호·계정을 재생성하지 않는다.
- 이미 적용된 Flyway SQL과 실제 회원·경기 기록은 수정하지 않는다. 과거 검증 화면 파일명과 설치 도구·IDE 설정의 기존 이름은 이력과 실제 경로를 보존한다.

## 인수 기준

1. 브라우저 제목·로그인·공통 화면에서 조축ON이 서비스명으로 보이고, 로그인 후 HANA FC가 소속 팀명으로 구분된다.
2. 로그인 후 기존 선수·경기를 조회할 수 있고, 로그아웃·권한 검사·API 경로가 기존대로 동작한다. 팀 생성·전환·공유 코드 기능이 구현된 것처럼 표시되지 않는다.
3. 새 Java 패키지·시작 클래스와 프론트 패키지 이름으로 테스트·빌드할 수 있고 새 로컬 실행기 이름이 실제 파일과 일치한다.
4. 기존 환경변수·DB·영구 볼륨을 사용해 실행할 수 있다. 기존 Flyway 파일의 체크섬과 운영 데이터가 이름 변경으로 바뀌지 않는다.
5. 다운로드 파일명·문서·설정 예시가 새 명칭을 사용한다. 유지할 이전 이름은 실제 팀명·로컬 경로·데이터 호환성·검증 이력으로 설명할 수 있다.
6. 원격 저장소 이름 변경·업로드·CI 확인은 각 작업 결과를 별도로 기록한다. 코드 변경만으로 GitHub 변경이나 AWS 배포 성공을 선언하지 않는다.

## 작업과 검증의 분담

기획은 이 문서의 범위·규칙·화면 흐름을 관리한다. 디자인·퍼블리싱·프론트는 제품·팀 표시와 화면을, 백엔드는 패키지·설정·양식 이름을 맡는다. 총괄은 공유 설정·실행기·저장소 변경을 조율하고 파일 담당을 겹치지 않게 배정한다.

통합 후 Docker 없는 테스트와 MySQL 통합 테스트를 구분해 실행하고, 브라우저에서 제품·팀 표시와 기존 조회 흐름을 확인한다. 실제 데이터를 새로 넣거나 수정하지 않아도 검증할 수 있는 항목부터 확인한다. 사용자는 표시된 서비스·팀 구분과 사용 흐름을 최종 확인한다.
