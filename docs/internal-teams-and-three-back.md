# 자체전 사전 팀 배정과 3백 배치 변경

2026-10-15 · 로컬 개발 · 운영 배포 전

[설명 그림](diagrams/internal-team-workflow.svg) · [그림 생성 원본](../scripts/Generate-InternalTeamWorkflow.mjs)

## 요구사항과 정책

- 3-5-2: GK, LCB·CB·RCB, LWB·RWB, CM 두 명, CAM, ST 두 명. CAM을 앞에, 윙백을 양쪽에, CM 둘을 조금 뒤에 둔다. 작은 화면도 같은 공간 관계를 유지한다.
- 3-4-3: GK, LCB·CB·RCB, LM·CM·CM·RM, LW·ST·RW.
- 선수 카드는 기존의 모서리가 둥근 네모를 사용한다. 한눈에 보기와 일반 작전판 모두 같은 자리 구성을 사용한다.
- 자체전은 01에서 참석 예정자를 선택하고 각 선수의 A/B팀을 직접 정한다. 자동 팀 나누기는 이번 범위가 아니다.
- 02의 자동 편성, 드래그, 직접 배치, 한눈에 보기 편집은 01에서 정한 팀을 따른다. A 선수는 B 계획에 배치할 수 없다.
- 양 팀의 자동 편성은 각 팀 인원과 포메이션에 기존 GK·출석·교체·휴식 정책을 각각 적용한다. 두 결과를 모두 받은 뒤 초안에 반영한다. 한 팀 계산이 실패하면 기존 계획을 보존한다.
- 03은 실제로 있었던 일을 기록한다. 사전 팀 구분으로 실제 출전·득점 기록을 지우거나 막지 않는다. 같은 쿼터에 양 팀 중복 출전할 수 없는 기존 검증은 유지한다.

## 화면 흐름 / 스토리보드

| 단계 | 화면과 조작 | 저장·예외 |
| --- | --- | --- |
| 01 투표·출석 | 자체전 선택 → 참석 예정 선수 선택 → 선수별 A/B 선택, 미배정 인원 확인 | 팀 배정 자체를 경기와 함께 저장한다. 계획이 없는 중간 상태도 저장할 수 있다. |

| 02 스쿼드 계획 | A/B와 각 포메이션 선택 → 팀별 후보 배치 또는 양 팀 자동 편성 | 참석 예정 미배정자는 먼저 01에서 팀을 정한다. 서버도 잘못된 팀의 계획을 거절한다. |
| 03 실제 출전 | 계획을 실제로 복사하거나 직접 기록 | 계획 복사 시 배정 일치 여부를 확인한다. 이후 실제 변경과 골·도움·FK·PK는 기존 방식으로 입력한다. |
| 저장 후 재조회 | 해당 경기 수정으로 다시 진입 | 팀 배정, 계획, 포메이션, 실제 기록이 재현된다. |

## 데이터와 호환성

- 참가자 `plannedTeam`은 A/B 또는 미배정(null)이다. 실제 출석 상태나 선수 프로필의 소속과 별개다.
- 신규 요청은 `plannedTeamSpecified`로 명시적 미배정과 구버전의 필드 생략을 구분한다. 필드를 생략한 기존 저장 재시도의 지문을 바꾸지 않는다.
- Flyway V26은 저장된 3-5-2의 CDM 자리를 CAM으로, 3-4-3의 LWB/RWB를 LM/RM으로 옮긴다. 선수 ID·교체 순서·골·도움·FK·PK는 유지한다. 중앙 CB의 내부 코드 CCB는 유지하고 화면에는 CB로 표시한다.
- V27은 기존 자체전 계획에서 한 팀에만 배치된 선수의 팀을 복원한다. 여러 쿼터에서 A/B 양쪽에 있었던 선수는 임의로 정하지 않고 미배정으로 남긴다. 다시 계획을 수정할 때 운영진이 정한다.
- 변경 이력의 원본 스냅샷과 전송 결과가 불명확한 저장 요청은 과거 사실과 요청 식별을 보존한다. 편집 가능한 구버전 초안의 자리 변환과 고정된 재전송 요청을 구분한다.
- 팀을 변경해도 실제 기록은 보존한다. EXTERNAL 경기에는 사전 A/B 배정을 저장하지 않는다.

## 검증 기준

1. 두 포메이션 모두 GK 포함 11자리, 중복 없는 내부 코드와 표시를 가진다.
2. 320px·390px·데스크톱 작전판에서 카드가 겹치지 않고 CAM/CM/윙백과 LM/RM이 구분된다.
3. A/B 배정 후 저장·재조회, 미배정 중간 저장, 배정 변경 취소/확인, 후보와 드래그·한눈에 보기·복사·자동 편성의 같은 팀 제한을 확인한다.
4. 서버에서 다른 팀 계획을 거절하고, 03의 실제 팀 변경은 허용한다. 교체 0.5쿼터와 세부 득점을 보존한다.
5. V25 자료를 V27까지 올려 계획·실제 자리만 바뀌며 기록 수치가 유지됨을 검증한다. 과거 모호한 팀 배정은 null로 남는다.
6. 저장 재시도, 초안 복구, 감사 이력에서 신규 필드와 이전 형식을 함께 확인한다.

## 문서와 배포

회원용은 포메이션 표시, 운영진용은 추가로 01 팀 배정·02 팀별 편성·03 실제 기록 구분을 갱신할 대상이다. 운영 가이드 1.1과 기존 운영 포메이션 그림은 현재 배포판을 설명하므로 유지한다. 실제 기능 배포 준비 시 공통 원고·HTML/PDF·앱 내 가이드를 함께 갱신하고 배포 후 버전을 확정한다. 이 문서·그림의 업로드만으로 앱을 배포하지 않는다.

## 검증 결과 (2026-10-15)

- 프론트 전체 **223개**, TypeScript 검사·Vite 빌드 통과. 빌드의 500kB 청크 크기 경고는 남아 있다.
- Java 단위/API **441개**, 실행 JAR 빌드 통과. Docker 없이 격리 native MySQL 8.4에서 API **21개**와 V26/V27 마이그레이션 **5개**를 실행해 통과했다. XML 결과의 실패·건너뜀은 0이다. 이번 전체 Docker 통합 회귀는 실행하지 않았다.
- 새 nullable 참가자 필드로 영향을 받은 출석률 집계는 `count(p.playerId)`로 명확하게 집계하도록 수정하고 기존 출석률 테스트를 다시 통과했다.
- 별도 가상 팀의 22명으로 미배정 1명일 때 편성 차단 → A/B 배정 저장 → 두 팀 4쿼터 자동 편성 → 팀별 후보 확인 → 계획 저장 → 실제 복사를 확인했다.
- 03 CAM에 1골 입력 후 그 선수의 사전 팀을 A에서 B로 변경했다. 확인을 거쳐 A 계획의 해당 선수만 해제되고 실제 A팀 CAM 1골은 유지됐다. 저장·새로고침 후 B 배정도 확인했다.
- 390px 한눈에 보기에서 두 포메이션과 01의 4열 팀 배정을 시각 확인했다. 320px 한눈에 보기에서 두 포메이션 11장의 겹침·구장 밖 넘침이 없었고, 3-5-2 실제 작전판은 320/390/1440px에서 11자리의 겹침·구장 밖 넘침이 없었다. 긴 가상 선수명은 카드에서 줄이거나 생략하고 상세에서 확인할 수 있다.
- 실제 iPhone Safari 터치, 전체 Docker 통합 회귀, 운영 DB 마이그레이션과 배포는 아직 하지 않았다. UI 검증은 가상 팀에만 저장했다. 로컬 미리보기 DB는 변경 전에 DPAPI 암호화 백업을 만들었으며 원본 팀 DB·운영 서버는 유지했다.
