## 판단

조기축구의 실제 운영 규칙을 담는 기능과 저장 보호는 잘 갖춰졌다. 이제는 **많은 기능을 한꺼번에 설명하는 화면에서, 지금 필요한 행동과 결과를 먼저 보여주는 화면으로 정리할 때**다. 화면이 예쁘지 않아서만 어려운 것이 아니다. 조회 전에 기간·경기 구분·집계 기준·정렬을 연속해서 읽어야 하고, 경기 수정 시에도 이미 정한 기본 정보가 큰 공간을 차지한다.

새로운 프레임워크나 서버로 교체할 필요를 뒷받침하는 근거는 이번 검토에서 찾지 못했다. 현재 Spring/React/MySQL 구조를 유지하고 사용성, 백업, 계정 회복, 검증 자동화를 먼저 개선하는 편이 적절하다.

## 이번 구현 범위와 스토리보드

### 회원 / 운영진 공통 조회

`선수 기록 → 적용 기간·경기 조건 요약 → 경기 요약 → 선수 찾기 → 간단 보기 또는 표 → 선수 상세 → 원본 경기`

- 680px 이하에서 처음 열면 간단 보기, 넓은 화면에서는 표로 시작한다. 선택한 보기 방식은 상세에서 돌아와도 유지한다. 재접속 간 설정 저장은 이번 범위가 아니다.
- 간단 보기: 등번호·이름, 득점·도움·출전 쿼터·출석, 출전 경기 수. FK/PK는 실제 해당 득점이 있을 때 표시한다.
- 같은 `selectStats` 결과와 `displayScoringValue`를 사용한다. 보기 전환으로 필터·정렬·집계 값이 바뀌지 않는다.
- 표의 열 제목 정렬은 유지하고, 간단 보기에는 정렬 기준/방향 버튼을 제공한다.
- 기간을 변경만 하고 적용하지 않았으면 접어도 ‘변경한 기간 미적용’을 표시한다. 잘못된 범위는 기존 결과를 유지한다.
- 선수 필터는 선택한 연령대·직책·포지션을 요약하며 접힌 상태에서도 초기화할 수 있다.
- 대회 목록 조회 실패 시 경기 조건을 펼쳐 오류와 재시도를 보여준다. 다시 접어도 ‘대회 목록 확인 필요’가 남는다.

### 감독 / 코치 경기 수정

`기존 경기 열기 → 날짜·시간·상대 요약 → 저장했던 단계 → 필요할 때 기본 정보 펼침 → 저장`

- 새 경기는 필수 정보 입력이 필요하므로 기본 정보를 펼친다.
- 접힘은 입력을 제거하지 않는다. 초안과 경기 배치 값은 계속 유지한다.
- 날짜/시간/구간 오류 또는 연결 대회 정보 조회 실패는 해당 영역을 펼친다. 저장 오류는 접기 밖에서 표시한다.
- 저장·완료·초안 보관 정책, 서버 API, DB 구조는 변경하지 않았다.

## 추가하면 좋은 기능의 순서

1. **최근 경기와 이어서 작성 첫 화면.** 운영진에게 미완료 경기 한두 건과 ‘새 경기’를 우선 노출한다. 회원은 최근 스코어와 기록 검색을 먼저 본다. 새로운 대시보드 수치를 늘리지 않는다.
2. **선수 활동 중지/복귀.** 쉬는 회원을 지워서 과거 기록이 망가지지 않게 한다. 활동 상태와 계정 권한은 별개로 유지한다.
3. **안전한 이전 경기 복사.** 장소·예정 명단·포메이션을 선택해서 복사한다. 실제 출석·득점·스코어·완료 상태는 새 경기에서 비우는 정책을 먼저 합의한다.
4. **팀 공유용 결과/스쿼드 이미지.** 팀원이 재방문하지 않아도 단톡방에서 확인하기 좋다. 민감한 계정 정보와 코드가 섞이지 않게 공유 전 미리보기를 둔다.
5. **내 기록 고정.** 공유 코드 회원은 개인 신원이 없으므로 ‘이 기기에서 즐겨찾는 선수’ 정도로 시작할 수 있다. 본인 인증이나 개인 계정인 것처럼 표현하지 않는다.

프로 선수 비교·가상 몸값·네이티브 앱은 기록 입력의 부담과 복구 체계를 다듬은 뒤 진행하는 것이 좋다. 외부 API 선정은 기존 결정대로 보류한다. 출석률/연말 시상/분 환산 정책을 임의로 확정하지 않는다.

## 배포·인프라 제안

- **당장 이전하지 않는다.** 현재 구조는 웹/API/DB의 책임이 명확하다. 사용자가 느끼는 긴 화면은 서버 이전으로 해결되지 않는다.
- 먼저 백업 성공 시각·실패 알림·독립 암호화 사본·복원 키 보관을 정리한다. Windows DPAPI 사본은 현재 사용자/PC에 종속되어 PC 분실 대책이 아니다. [운영 백업의 실제 상태](backup-recovery.md).
- 배포는 검증된 커밋을 기준으로 시험 환경→자동 검증→백업/복구 경계 확인→운영 승인→동작 점검 순서를 유지한다. 시험 환경도 실제 선수 데이터를 복제하기보다 가상 데이터로 검증한다. 새 클라우드 자원은 만들지 않았다.
- API 지연·부하·비용을 측정해 요구가 생겼을 때 리전이나 호스팅을 비교한다. Oracle 용량 확보는 백업·보안 패치·장애 대응까지 자동으로 해결하지 않는다.
- 이번에는 요금표나 콘솔을 재조회하지 않았다. 새로운 무료 서비스나 무중단/무료 보장을 제안하지 않는다.

## 수행한 검증

- `pnpm --filter @jochook-on/web build`: TypeScript 검사와 Vite 빌드 성공. 큰 번들 경고는 남음. 최초 sandbox `spawn EPERM` 후 허용된 로컬 빌드로 재실행.
- `node --test --test-isolation=none tests/*.test.mjs` (frontend): 기존 245개 테스트 통과. 기간/정렬/쿼터 계산/초안/재시도/팀 범위 회귀 포함. 새 UI 시나리오는 아래 브라우저 점검으로 확인.
- 가상 전용 localhost 응답, 실제 DB 연결 없음, POST/PUT/DELETE는 거절하는 미리보기 사용.
- 320px/390px 페이지 가로 넘침 없음 확인. 1280px 초기 표 보기 확인. 실제 iPhone Safari 에뮬레이션은 아님.
- 카드 등번호 오름/내림과 표 순서 일치, 상세 복귀 초점·보기 유지, 0쿼터 환산 — 표시 확인.
- 기간 오류→기존 조회 유지, 미적용 표시, 전체 기간 전환 확인. 선수 필터 요약/초기화 확인.
- 기존 경기 접힘/신규 펼침, 시작 시를 지우고 접은 뒤 저장 검증 시 자동 펼침 확인. 가상 선수 배치 유지. DB 저장 요청 전에 막히는 시나리오다.
- 대회 목록 503 가상 응답에서 조건 자동 펼침·재시도·요약 경고 노출 확인.
- 회원 역할 화면에서 경기 등록·삭제 버튼 없음 확인. 이는 UI 검증이며 서버 권한 통합 재실행을 대체하지 않는다.
- 390px 동일 가상 데이터·초기 조건에서 첫 기록 위치: **1,809.125px → 1,363px**, 약24.7% 감소. 네트워크나 입력 소요 시간을 측정한 값이 아니다. [전](diagrams/project-review-2026-10-16/stats-mobile-before.png) / [후](diagrams/project-review-2026-10-16/stats-mobile-after.png).

수행하지 않은 검증: Java/Dockerless 백엔드 테스트·Docker/native MySQL 통합 재실행, 운영 DB 쓰기, 클라우드 라이브 상태, 실제 iPhone, 전체 보안 침투 시험. 서버 코드는 이번에 읽기 검토만 수행했다.

## 가이드·그림·배포 경계

- 회원용: 접힌 조회 조건·스탯 기준·간단/표 전환 안내가 필요하다.
- 운영진용: 위 공통 변경과 기존 경기 기본 정보 펼치기 안내가 필요하다.
- **가이드 1.2의 운영 원고/PDF는 그대로 유지**한다. 배포 전에는 이 문서를 개발 명세로 사용하고, 실제 배포 시 `docs/guides/content.json`, 앱 목차/역할별 화면, HTML·PDF를 함께 반영·렌더 검증한다.
- DB·스택·실제 인프라 구조 변경이 없으므로 ERD와 현재 시스템 구성도는 변경 대상이 아니다. 이번 진단 그림과 생성 소스만 추가했다. 기존 미추적 `scripts/database-schema.mjs`는 별도 작업으로 보존했다.
- 그림 생성: `node scripts/Generate-ProjectReview.mjs`. PNG도 갱신할 때는 `JOCHOOK_SHARP_MODULE`에 설치된 sharp 모듈 경로를 지정한다.
- 미배포 코드와 함께 결과물을 Git 추적 경로에 준비했다. GitHub 공유는 `codex/project-review-2026-10-16` 검토 브랜치로 분리하며 main 병합·운영 배포는 이번 작업에 포함하지 않는다.

## 사용자 확인 제안

가상/로컬 화면에서 ① 기간 바꾸기 ② 간단 보기 정렬 ③ 선수 상세와 복귀 ④ 기존 경기 수정 ⑤ 새 경기 등록을 각각 한 번 해본다. 무엇을 눌러야 할지 망설이는 지점과 불필요하게 접고 펼치는 곳을 알려주면 다음 첫 화면 설계에 반영한다. ‘사용하기 쉬워졌다’는 판단은 이 확인 뒤 확정한다.
