# 경기 기록 작성 상태

## 요구사항과 운영 규칙

- 경기 목록에 마지막 저장한 작성 상태를 표시하고 다시 열면 이어서 작성한다.
- 상태는 `ATTENDANCE`(01 투표·출석), `PLAN`(02 스쿼드 계획), `ACTUAL`(03 실제 출전), `RESULT`(04 결과·코멘트), `COMPLETED`(기록 완료)다. 작성 중 상태는 누락된 필수 항목 수나 이전 단계 완료 여부를 뜻하지 않는다.
- 하단 **중간 저장 · 목록으로**는 현재 탭을 작성 중인 단계로 저장한다. 탭을 보기만 하거나 저장하지 않고 나가면 DB 상태는 바뀌지 않는다.
- 각 단계의 **저장 · 다음 단계로**는 입력 전체와 다음에 작성할 단계를 함께 저장한다. 03의 **02 계획대로 참석·출전 기록 저장**은 03 작성 중을 유지한다.
- 04의 **기록 완료 · 목록으로**를 직접 눌렀을 때만 완료다. 점수 0이나 빈 코멘트로 자동 판단하지 않는다. 기존 필수 기본 정보와 데이터 유효성 검사는 유지하되 모든 자리·코멘트·점수 입력을 강제하지 않는다. 운영진이 필요한 범위의 기록을 확인한 의미다.
- 완료한 경기에서 중간 저장하면 해당 단계의 작성 중으로 돌아간다. 완료를 유지하며 수정하려면 04에서 다시 기록 완료한다. 별도 수정 잠금은 도입하지 않는다.
- 기존 경기는 과거 완료 결정을 알 수 없어 **기존 기록 · 상태 미지정**으로 표시한다. 다음 저장부터 상태가 지정된다. 신규 요청에 상태가 없으면 01로 시작하며, 구버전 클라이언트의 수정 요청에서 상태 생략 시 기존 값을 보존한다.
- 감독·코치만 상태와 기록을 저장한다. 회원은 목록 상태와 기록을 조회한다. 기존 팀 격리·수정 버전 충돌 검사는 그대로 적용한다.
- 상태 변화도 기존 경기 변경 이력의 전후 스냅샷과 비교 화면에 남긴다. 통계 집계 포함 여부는 변경하지 않는다.

## 화면 흐름

1. 01에서 투표 입력 → 중간 저장 → 목록 카드에 **01 투표·출석 작성 중**, **이어서 작성** 표시.
2. 목록 카드 선택 → 저장된 단계 탭을 선택해 연다. 편집 상단에는 마지막 저장 상태를 보여준다.
3. 02 계획 저장 → 03으로 이동. 나중에 목록에서도 **03 실제 출전 작성 중**으로 확인한다.
4. 04에서 중간 저장 → **04 결과·코멘트 작성 중**. 기록 완료 클릭 → 초록색 **기록 완료**, 목록으로 복귀.
5. 완료 경기를 다시 열면 04에서 확인한다. 기존 상태 미지정 경기는 01에서 시작한다.

## 구현과 확인 기준

- V20은 `match_records.recording_stage`에 nullable VARCHAR와 허용값 CHECK 제약을 추가한다. 기존 데이터와 적용된 마이그레이션은 수정하지 않는다.
- 목록·상세 API 및 요청에 `recordingStage`를 추가한다. 데이터와 상태를 같은 트랜잭션으로 저장해 실패 시 함께 롤백한다.
- 프론트의 상태 결정·재개 단계 및 변경 이력 테스트, Java 기본값·명시적 완료·되돌림·구버전 호환 테스트를 수행한다. MySQL에서 마이그레이션, 저장→목록→재조회, 변경 이력, 충돌 시 상태 보존을 확인한다.
- 프론트 단위 테스트가 TypeScript 모듈을 직접 실행하므로 명시적 `.ts` import를 허용한다. `noEmit`을 유지하고 번들은 기존 Vite가 담당한다.
- 운영 배포와 Git push는 별도 요청 전까지 수행하지 않는다. 실제 데이터가 없는 임시 미리보기에서는 상태 예시만 제공하고 저장 요청은 계속 차단한다.

## 검증 결과 (2026-10-15)

- `pnpm --filter @jochook-on/web test`: 45개 통과. `pnpm build`: TypeScript와 Vite 통과.
- `scripts/Start-Backend.ps1 -Task test`: Docker 없는 Java/API 테스트 211개 통과. `bootJar`도 성공했다.
- Docker Desktop 엔진이 시작되지 않아 Testcontainers 통합 테스트 전체는 실행하지 못했다. 대신 `work/recording-qa`의 새 데이터 디렉터리와 3322/8092 루프백 포트에서 네이티브 MySQL 8.4·실제 API를 격리 실행했다.
- 격리 DB에서 V1~V20 Flyway 적용과 Hibernate 스키마 검사, 외부 경기·자체전의 단계 변경 5회씩, 저장 후 목록·상세 일치, 완료→작성 중 변경 이력, 오래된 버전 409, 잘못된 상태 400, 구버전 요청의 상태 보존을 확인했다.
- 이전 구조를 재현한 별도 가상 테이블에 V20을 적용해 기존 컬럼 값 전체가 보존되고 이전 경기 2건의 상태가 NULL인 것을 확인했다. 실제 선수·회원 DB에는 연결하지 않았다.
- 390px 브라우저에서 목록 상태 배지, 03 작성 중 경기를 열면 03 선택, 완료 경기를 열면 04 선택, 04에만 완료 버튼이 표시됨을 확인했다. 실제 iPhone Safari 검증은 사용자 확인이 필요하다.
- 임시 공개 미리보기는 가상 데이터 조회만 허용한다. 실제 저장 기능 검증은 위 격리 API에서 수행했으며 운영 서버·GitHub에는 배포하지 않았다.
