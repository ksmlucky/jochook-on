# 팀 생성·팀 코드 접속 요구사항 정의서

작성일·구현 승인일: 2026-10-14 · 기존 팀 기능은 **로컬 V16 적용·통합 검증 완료**다. 사용자가 코드 90일·초대 24시간 정책을 채택했고 백엔드·프론트와 V14~V16을 구현했다. 당시 Java 단위/API 159개·MySQL 통합 46개·프론트 19개 및 데이터 보존 결과는 [검증 기록](verification.md)에 남겼다. **추가 요청인 코드+자동 생성 팀 비밀번호도 V17 로컬 적용·자동 검증 완료**이며, 아래 관련 정책을 새 구현 기준으로 갱신했다. 공개 클라우드 배포는 아직 하지 않았다. 기존 화면은 [스토리보드](team-access-storyboard.md), 비밀번호 추가 화면은 [추가 명세](team-code-password.md), 요청·응답은 [API 계약](team-access-api.md)을 따른다.

이번 추가 변경은 감독·코치 역할 분리와 감독의 코치 관리다. 아래 현재 정책에 반영했으며 [감독·코치 명세](team-staff-permissions.md)의 세부 인수 기준도 적용한다. V18 적용·검증 완료 여부는 별도의 검증 기록으로 확인한다.

## 1. 목표와 이번 범위

조축ON의 서비스 관리자가 팀을 만들고 최초 감독을 지정한다. 감독과 코치는 개인 계정으로 본인 팀의 기록과 조회 접속 정보를 관리하며, 감독은 해당 팀 코치를 임명·해제한다. 회원은 전달받은 팀 코드와 팀 비밀번호로 계정 없이 해당 팀의 선수단·경기 기록을 조회한다.

이번 기능에 필요한 것은 팀 생성, 운영진 지정·활성화, 코드 발급·재발급·폐기, 코드 조회 접속, 팀별 데이터·권한 분리다. 회원 개인 가입, 공개 팀 검색, 타 팀 운영진의 직접 팀 생성, 자동 문자·이메일 발송, 결제, 팀 삭제·통합은 후속 범위다. 코드 원문이나 계정 정보를 문서·예시 데이터에 넣지 않는다.

## 2. 구현 착수 전 상태와 확정한 요구사항

다음 표의 ‘착수 전’은 변경 이유를 설명하는 과거 상태다. 현재는 실제 팀·소속·코드·초대 모델과 팀별 데이터 경계를 구현했다.

| 구분 | 내용 |
| --- | --- |
| 착수 전 구현 | 조축ON 서비스명과 HANA FC 표시명 분리. 팀명은 프론트 표시 설정이며 실제 팀 소속 기능은 없다. |
| 착수 전 인증 | 개인 계정의 전역 ADMIN/MEMBER 역할과 30분 유휴 세션, 로그인·로그아웃·CSRF 검사. 서비스 관리자·팀 운영진 구분은 없다. |
| 착수 전 데이터 | 선수·경기에 팀 소유 정보가 없고 활동 등번호 중복 제한은 전체 명단 기준이다. 팀 코드·운영진 초대는 없다. |
| 보존 기준 | 기존 HANA FC의 회원 37명·경기 2건과 연결된 투표·출석·계획·출전·득점 기록을 보존한다. 수치는 기존 확인값이며 실제 이전 직전 다시 확인한다. 명단·개인정보는 이 문서에 싣지 않는다. |
| 사용자 확정 D-01 | **사용자 본인이 서비스 관리자로 팀을 만들고 최초 감독을 지정한다.** 서비스 관리자의 운영진 지정 기능을 유지하고, 추가 요청으로 감독이 현재 팀 코치를 관리한다. 타 팀 운영진의 공개 팀 생성은 이번 범위가 아니다. |
| 사용자 확정 | 회원은 공유 코드와 발급 시 자동 생성되는 팀 비밀번호로 개인 계정 없이 조회하고, 운영진은 개인 계정으로 수정한다. 발급·재발급·폐기는 해당 팀 운영진만 가능하다. |
| 추가 구현 기준 | 기존 12자 코드에 독립적인 숫자 6자리 팀 비밀번호를 함께 사용한다. 6자리 길이는 총괄의 권고를 이번 구현 기준으로 사용하며 개인 계정 비밀번호나 2FA로 취급하지 않는다. |
| 사용자 확정 | 재발급·폐기 시 이전 코드와 그 코드로 접속한 조회 세션을 무효화한다. 운영진의 개인 로그인 세션과 구분한다. |
| 필수 설계 | 실제 팀·운영진 소속·선수/경기의 team_id를 도입해 조회와 변경을 팀별로 분리한다. 화면의 팀 이름만 바꾸어 다른 팀처럼 제공하지 않는다. |

## 3. 역할과 권한

서비스 관리 플래그 `SERVICE_ADMIN`과 팀 소속 역할 DIRECTOR(감독), COACH(코치), MEMBER(조회)를 구분한다. 아래 `운영진`은 감독과 코치를 함께 가리키며, 임명 권한은 역할별로 다르다. 코드 조회자는 개인 계정 없이 MEMBER 조회 세션을 만든다.

| 작업 | 미접속 | 코드로 접속한 회원 | 해당 팀 운영진 | 서비스 관리자 |
| --- | --- | --- | --- | --- |
| 코드 입력·운영진 로그인 | 가능 | 전환 흐름으로 가능 | 로그아웃·전환 흐름으로 가능 | 로그아웃·전환 흐름으로 가능 |
| 소속 팀 선수·경기 조회 | 불가 | 접속한 팀만 | 소속 팀만 | 팀 운영진 소속이 있을 때만 |
| 선수·경기·용병 등록/수정, 엑셀·자동 편성 | 불가 | 불가 | 소속 팀만 | 팀 운영진 소속이 있을 때만 |
| 코드 발급·재발급·폐기 | 불가 | 불가 | 소속 팀만 | 팀 운영진 소속이 있을 때만 |
| 팀 생성·최초 감독 지정 | 불가 | 불가 | 불가 | 가능 |
| 현재 팀 코치 임명·초대·해제 | 불가 | 불가 | 감독만 가능 | 서비스 팀 관리에서 가능 |
| 서비스 팀 목록·운영진 지정 상태 조회 | 불가 | 불가 | 본인 팀 정보만 | 가능; 선수·경기 전체 열람 권한은 아님 |

서비스 관리 권한과 팀 운영 권한은 별개다. 사용자 본인의 기존 계정을 `JOCHOOK_ON_SERVICE_ADMIN_USERNAME` 운영 초기 설정으로 명시하고 HANA FC 팀 운영 권한을 함께 유지한다. DB는 `accounts.service_admin`과 `team_memberships.role/active`를 구분한다. 기존 ADMIN 계정 전부를 자동 승격하거나, 가장 먼저 가입한 사람·팀 코드를 아는 사람에게 서비스 관리 권한을 주지 않는다. 선수 직책인 회장·감독·코치·총무·정회원도 로그인 권한과 별개다.

V18에서 기존 ADMIN 소속과 구 운영진 초대는 COACH로 이전한다. 사용자가 초기 감독 지정을 위임했으므로 현재 유일한 로컬 초기 관리자 계정 하나를 첫 DIRECTOR로 명시적으로 지정하기로 했다. 신규 계정을 모두 감독으로 만드는 규칙은 아니며, 나중에 서비스 관리 화면에서 실제 감독 계정으로 인계할 수 있다.

## 4. 요구사항 목록

아래 요구사항과 5절의 기존 추천 정책은 사용자 승인을 받아 이번 구현 기준으로 확정했다. `확정`은 구현 성공이나 테스트 통과를 뜻하지 않는다. 화면 ID는 TA-S, 인수 기준은 TA-A로 연결한다.

| ID | 상태 | 요구사항 | 화면 | 인수 기준 |
| --- | --- | --- | --- | --- |
| TA-R01 | 확정 | 서비스명 조축ON과 접속한 팀명을 구분한다. 미접속 홈은 코드·팀 비밀번호를 한 화면에서 입력하고 운영진 로그인 경로를 제공한다. | S01·S02·S08, TCP-S01 | A01 |
| TA-R02 | 확정 | 서비스 관리자만 팀을 생성하고 최초 감독을 지정한다. 같은 요청의 재시도로 팀을 중복 생성하지 않는다. | S03·S04 | A02·A03 |
| TA-R03 | 확정 | 서비스 관리자는 감독/코치, 현재 팀 감독은 코치만 기존 로그인 ID로 지정하거나 일회용 초대로 활성화한다. 신규 초대에서 이미 존재하는 ID를 사용하려면 해당 계정 로그인 후 수락하며 비밀번호를 덮어쓰지 않는다. | S03·S04·S05, TS-S02·S03 | A04·A05, TS-A07·A08 |
| TA-R04 | 확정 | 운영진은 본인의 활성 소속 팀만 선택·수정한다. 서비스 관리 권한만으로 팀 기록 권한을 얻지 않는다. | S02·S03·S09 | A06·A07 |
| TA-R05 | 확정 | 해당 팀 운영진만 회원 조회 코드와 자동 생성 팀 비밀번호를 함께 발급한다. 팀당 활성 조합은 1개다. | S06·S07, TCP-S02 | A08 |
| TA-R06 | 확정 | 재발급은 두 값을 함께 바꾸고, 재발급·폐기는 이전 조합과 그 코드의 모든 조회 세션을 무효화한다. 운영진 개인 로그인은 유지한다. | S06·S07·S10, TCP-S03 | A09 |
| TA-R07 | 확정 | 회원은 유효한 코드·팀 비밀번호 조합으로 계정 없이 그 팀만 조회한다. 소지는 수정 권한이나 개인 신원 확인으로 취급하지 않는다. | S01·S08, TCP-S01 | A10 |
| TA-R08 | 확정 | 목록·상세·검색·합계·자동 편성·엑셀·용병·수정의 모든 경로에서 팀 범위와 소속을 확인한다. 다른 팀 선수의 기록 연결도 거부한다. | 전체 | A11·A12 |
| TA-R09 | 확정 | 팀/접속 방식 변경 시 미저장 내용을 확인하고, 이전 팀 데이터·캐시·진행 중 응답이 새 화면에 섞이지 않게 한다. 요청에는 기대하는 팀을 함께 보내며 서버의 현재 세션·소속과 불일치하면 저장을 거부한다. | S01·S03·S09 | A13 |
| TA-R10 | 확정 | 기존 HANA FC를 실제 팀으로 연결하고 기존 계정·선수·경기·연결 기록을 보존한다. | S03·S08 | A14 |
| TA-R11 | 확정 | 오류는 현재 상태와 다음 행동을 안내한다. 코드·초대·계정 실패에 대한 재시도 제한과 요청 중 중복 클릭 방지를 둔다. | S01·S02·S04·S05·S06·S10 | A03·A05·A15 |
| TA-R12 | 확정 | 코드·팀 비밀번호 원문은 발급 성공 화면에서 한 번만 보여 주고 개별 복사한다. 목록에는 상태·유효기간·발급 이력만 표시한다. 분실하면 두 값을 재발급한다. | S06·S07, TCP-S02 | A08·A16 |
| TA-R13 | 확정 | 서비스 관리자는 감독/코치 초대와 소속을 관리하며 마지막 활성 감독은 대체 감독 활성화 전 해제/강등하지 못한다. 감독은 본인 팀 코치 초대를 관리하고 COACH를 MEMBER로 바꿀 수 있으나 감독 소속·초대는 변경하지 못한다. | S03·S04·S05, TS-S02 | A04·A17, TS-A09·A10·A11 |

## 5. 승인된 운영 정책

아래 정책은 기존 승인 기준에 팀 비밀번호와 감독·코치 추가 요청을 반영한 현재 기준이다. 숫자 6자리는 총괄의 권고를 반영한 구현 기준이다. 정책 결정과 실제 적용·검증 결과는 구분한다.

| ID | 주제 | 확정 정책과 이유 |
| --- | --- | --- |
| P01 | 팀 입력·동일 팀명 | 팀명 2~40자 필수, 앞뒤 공백 제거. 지역/구분 설명 40자 이내 선택. 동일 팀명은 허용하고 내부 팀 ID로 구분한다. 관리자 목록에 지역/설명을 함께 보여 잘못 선택하지 않게 한다. 팀명만으로 소속을 부여하지 않는다. |
| P02 | 팀 생성·중복 요청 | 팀 생성과 기존 계정 소속 지정 또는 신규 초대 생성은 한 번에 성공/취소한다. 신규 팀은 첫 운영진 활성화 전 ‘운영진 설정 대기’로 표시한다. 동일 요청 재시도는 같은 팀/초대 상태를 반환한다. 응답이 불명확하면 목록을 확인하고 무조건 다시 만들지 않는다. |
| P03 | 최초 감독·코치 활성화 | 최초 감독은 서비스 관리자가 정확한 기존 로그인 ID로 지정하거나 DIRECTOR 초대를 발급한다. 기존 계정 지정은 수락 링크 없이 해당 계정 로그인 후 사용할 수 있다. 감독은 현재 팀에 COACH만 직접 지정/초대한다. 초대는 팀·역할·초대 건에 연결한 일회용 링크이며 확인한 사람에게 개인 전달한다. 유효기간 24시간, 대상자가 ID·비밀번호 설정, 자동 이메일 발송 제외 정책을 유지한다. |
| P04 | 초대와 계정 충돌 | 사용할 ID가 이미 있으면 기존 계정으로 로그인해 초대를 수락해야 한다. 비밀번호를 덮어쓰거나 이름·연락처만으로 계정을 합치지 않는다. 초대 재발급/취소 시 이전 링크는 무효다. 대상을 잘못 지정하면 취소 후 새로 지정한다. 사용·만료된 링크는 권한을 만들지 않는다. |
| P05 | 운영진 관리 | 서비스 관리자는 감독/코치 소속을 지정·해제한다. 감독은 현재 팀 코치만 임명하거나 MEMBER로 전환한다. 마지막 활성 감독의 해제·강등은 대체 활성 감독이 있어야 하며 코치·미수락 초대는 대체자로 세지 않는다. 코치 관리로 감독·자신의 권한을 변경하지 않는다. 매 요청의 활성 소속을 검사하며 다른 팀 권한은 바뀌지 않는다. |
| P06 | 코드·팀 비밀번호 형태 | 혼동하기 쉬운 문자를 제외한 무작위 영문 대문자·숫자 12자 코드를 4자씩 구분해 표시한다. 코드 입력의 대소문자·공백·구분 하이픈 차이는 허용한다. 독립적인 무작위 숫자 6자리 팀 비밀번호를 함께 생성하고 앞 0을 보존하는 문자열로 처리한다. 이름·생년·등번호에서 두 값을 만들지 않는다. 팀명을 추가 입력하지 않으며 코드만 먼저 확인하는 API는 만들지 않는다. |
| P07 | 공통 유효기간 | 두 값 모두 발급 후 90일이다. 기간을 직접 조절하는 UI는 생략한다. 공통 만료일을 표시하고 만료 시 해당 코드의 조회 세션도 종료한다. |
| P08 | 원문 보관·재발급 | DB에는 코드 SHA-256 해시와 팀 비밀번호 BCrypt 해시만 저장하고 두 원문은 발급 성공 응답에서 1회 제공한다. URL·로그·localStorage/sessionStorage·오프라인 캐시에 남기지 않는다. 다시 보려면 두 값을 재발급하며 기존 조회 세션 종료를 먼저 안내한다. 응답을 잃으면 상태 확인 후 재발급한다. 동시 재발급은 조회한 version으로 충돌을 검사하고 두 값·버전·이력을 한 트랜잭션으로 갱신한다. |
| P09 | 조회·운영진 세션 | 조회 세션은 유휴 24시간/최대 7일, 운영진 개인 로그인은 현재의 유휴 30분이다. 코드 만료·폐기·재발급이나 팀/소속 비활성화가 더 빠르면 그 조건이 우선한다. ‘계속 로그인’ 기능은 추가하지 않는다. |
| P10 | 코드 무효화 시점 | 서버가 성공 처리한 재발급/폐기 이후 시작하는 이전 코드 기반 요청은 거부한다. 화면 포커스 복귀·새 요청 시 접근 상태를 확인해 팀 데이터를 지우고 재입력을 안내한다. 이미 본 내용·캡처까지 회수하는 기능은 아니다. 세션의 코드 버전과 DB의 현재 버전·기간·팀 상태를 매 요청 대조한다. |
| P11 | 접속 실패 | 틀린 코드·팀 비밀번호, 없는 코드, 만료·폐기는 같은 오류 응답과 안내를 사용한다. 존재하는 팀/계정이나 어느 값이 맞았는지 알려 주지 않는다. IP 및 브라우저 단위로 10분 내 실패 10회 후 10분 대기를 유지한다. 남은 대기시간과 재시도를 안내한다. |
| P12 | 팀·모드 전환 | 브라우저 세션은 한 번에 하나의 접속 방식·팀을 사용한다. 운영진은 소속 팀 목록에서 전환한다. 회원은 다른 팀의 코드·비밀번호 조합이 확인된 후 기존 조회 세션을 교체한다. 운영진에서 회원 조회로 바꿀 때는 미저장 확인 후 로그아웃하고 입력 화면으로 이동한다. |
| P13 | 기존 계정 이전 | 서비스 관리 권한은 명시적 설정으로만 부여한다. V18은 기존 ADMIN 소속과 구 운영진 초대를 COACH로 이전하고 MEMBER·계정 비밀번호를 보존한다. 사용자의 위임에 따라 현재 유일한 로컬 초기 관리자 계정을 별도로 첫 DIRECTOR로 지정한다. 모든 기존 관리자를 감독으로 자동 승격하지 않는다. 일반 회원 가입은 만들지 않는다. |
| P14 | 팀 상태 | 최초 운영진 미활성 팀은 조회 코드 발급 불가. 활성 팀만 코드 접속·기록 편집 가능. 팀 삭제·운영 중지 UI는 후속이며, 비활성 상태를 만나면 접근을 거부하고 운영자 문의를 안내한다. |
| P15 | 초대 발급자 권한 회수 | 초대 확인·수락 시 발급자가 현재 활성 서비스 관리자이거나, COACH 초대라면 해당 팀 활성 DIRECTOR여야 한다. 권한 상실 뒤 미사용 초대는 남은 기간이 있어도 거부한다. 현 권한자가 재발급하면 발급자도 갱신한다. COACH 초대 수락은 기존 활성 DIRECTOR를 낮추지 않는다. |

초기 관리자 활성화 링크와 회원 조회 코드는 목적·권한·유효기간이 다르다. 활성화 링크는 운영진에게 개인 전달하고, 회원 조회 코드는 단톡방 등에 공유한다. 회원 코드 입력 화면에서는 운영진 활성화를 실행하지 않는다.

신규 초대의 표시명 메모는 본인 인증 수단이 아니다. 개인 전달한 링크의 소지를 바탕으로 활성화하므로 다른 사람에게 전달하면 그 사람이 사용할 수 있다는 한계가 있다. 특정 기존 계정에 연결된 초대만 해당 계정으로 수락하도록 강제할 수 있다. 새 계정의 실명 인증 기능은 이번 범위에 없다.

## 6. 끊기지 않는 이용 흐름

1. 서비스 관리자가 개인 계정으로 로그인 → 서비스 팀 관리에서 새 팀과 최초 감독을 지정한다. 감독은 본인 팀의 코치 관리에서 코치를 임명·초대한다.
2. 기존 계정은 서비스 관리자가 정확한 로그인 ID를 확인해 소속을 직접 지정하고, 대상자는 해당 계정으로 로그인한다. 신규 초대 대상자는 개인 전달한 활성화 링크에서 새 계정을 만들거나, 이미 가진 계정으로 로그인해 해당 초대를 수락한다.
3. 활성화가 끝난 운영진은 본인 팀의 코드 관리에서 코드·팀 비밀번호를 함께 발급한다. 결과 화면의 개별 복사 버튼으로 두 값을 복사해 팀원에게 직접 공유한다.
4. 회원은 조축ON 홈의 한 화면에서 코드와 팀 비밀번호를 함께 입력한다. 두 값이 유효하면 해당 팀 이름과 기록을 조회하며 등록/수정·코드 관리 권한은 없다.
5. 재발급·폐기하면 이전 조합을 이용한 조회 요청은 종료된다. 회원은 새 코드와 팀 비밀번호를 받아 다시 입력한다. 비밀번호 없는 구 코드 역시 V17 이후 사용할 수 없으며 운영진 개인 로그인은 유지한다.

## 7. 데이터 연결과 기존 기록 이전 설계

이 절은 구현한 V14/V15와 실제 이전의 검증 기준이다. 문서 갱신은 SQL 실행이나 실제 이전 완료를 뜻하지 않으며, 실제 이전은 백업과 격리된 검증을 거쳐 진행한다. 상세 컬럼은 [DB 구조](database.md)를 따른다.

- 팀 식별 정보, 계정별 팀 소속·권한·상태, 팀별 조회 코드 상태를 별개로 관리한다. 로그인 계정과 선수 명단은 서로 다른 개념이다.
- 자체전 배치의 기존 `team=A/B`는 같은 클럽 안에서 나눈 경기 팀이다. 새 클럽 소속 `team_id`와 뜻이 다르며 기존 A/B 기록을 클럽 두 개로 바꾸지 않는다.
- 선수·용병과 경기 원본에 팀 소유 정보를 연결한다. 하위 출석·계획·출전 기록도 해당 경기와 선수의 팀이 같은지 DB 제약 또는 서비스 검증으로 보장한다. 클라이언트가 보낸 team_id만 믿지 않는다.
- 활동 등번호 중복 제한은 V15에서 **같은 팀 안의 활동 선수끼리** 적용하도록 바꿨다. 다른 팀의 같은 번호는 허용하고, 번호 없는 선수·같은 팀의 중복 거부 규칙은 유지한다.
- 기존 HANA FC 팀을 한 번 생성하고, 이전 직전 확인한 기존 회원 37명·경기 2건과 모든 연결 기록을 그 팀에 연결한다. 새 샘플 데이터로 대체하거나 선수·경기 ID를 다시 발급하지 않는다. 사용 중인 비밀번호 해시·계정도 보존한다.
- 기존 소속이 없는 계정·선수·경기를 방치하지 않는다. 백업 → 임시 DB에서 이전 검증 → 운영 이전 → 건수·ID·연결·핵심 값 대조 → 재조회 순서로 검증한다. V14는 팀 접속 모델, V15는 선수·경기 소속 연결이며 V1~V13은 수정하지 않았다.
- `auth/me`는 접속 방식 `authType`, 서비스 관리 권한 `serviceAdmin`, 현재 `team`, 활성 `teams`를 기존 username/role과 함께 반환한다. 선수·경기·코드 API의 `X-Team-Id`는 서버 세션과 일치해야 한다. 구체 형식은 [API 계약](team-access-api.md)을 따른다.
- 신규 운영진 초대는 무작위 32바이트를 43자 URL-safe 토큰으로 표현하며 원문은 성공 시 한 번 반환한다. 요청 재시도에서 원문을 재조회하지 않고 분실하면 재발급한다. 회원 조회 코드와 목적·길이·기간을 구분한다.

| TA-A14 | 이전 전후 기존 회원·경기와 하위 기록의 건수·ID·관계·핵심 값이 같다. 사용자 본인의 명시적 지정 외 기존 ADMIN에 서비스 관리 권한이 생기지 않는다. | R10 |
| TA-A15 | 코드 오류·접속 제한·통신 실패·세션 종료의 안내가 구분되고 성공처럼 이동하지 않는다. 원문 코드·회원 정보가 오류에 나오지 않는다. | R11 |
| TA-A16 | 발급 응답 유실 시 원문 복구가 불가함을 설명하고 상태 확인 후 재발급할 수 있다. 동시 재발급은 중복 성공처럼 안내하지 않는다. | R12 |
| TA-A17 | 대체 감독 활성화 전 마지막 활성 DIRECTOR 해제·강등은 막고, 초대 재발급 후 이전 링크는 사용할 수 없다. 코치·미수락 초대만으로 마지막 감독을 해제하지 않는다. | R13 |

## 9. 승인과 완료의 구분

- **기존 V16 구현과 로컬 검증 완료:** 당시 서비스 관리자의 팀 생성·공통 운영진 지정, 코드 접속·데이터 분리를 검증했다. 새 감독·코치 분리의 완료 근거로 재사용하지 않는다.
- **V17 검증 기록:** 코드 12자 + 독립적인 숫자 6자리 팀 비밀번호, 90일 공통 유효기간, 두 원문 1회 표시, 구 코드/세션 차단은 별도 검증 결과를 따른다.
- **추가 구현·검증 대상:** V18 역할 이전, 감독의 코치 관리, 역할을 포함한 초대, 초대 발급자 권한 확인, 마지막 감독 보호. 실제 로컬 적용과 테스트 완료는 검증 기록에서 확인한다.
- 유지 수치: 초대 24시간, 조회 세션 유휴 24시간/최대 7일, 운영진 유휴 30분, 접속 실패 10분 내 10회 후 10분 대기.
- 정책의 의미가 달라지는 변경은 승인된 범위와 대조하고 명세·스토리보드·개발 계약을 함께 갱신한다. 구현 방식은 총괄이 조율한다.
- 발급·재발급·폐기 이력은 V16으로 보완해 최근 20건을 운영진 화면에 제공하고 관련 API·브라우저 갱신을 검증했다. 실제 DB에는 HANA FC만 있고 조회 코드는 아직 미발급이다. HANA FC 실사용·복수 포메이션 지원 후 다른 팀을 도입한다. Oracle Cloud·Cloudflare 배포는 계정·무료 자원 준비부터 별도로 진행하며 아직 공개 서버에 배포하지 않았다.

## 10. 개발 검토 참고

- [OWASP Multi-Tenant Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html): 클라이언트의 팀 식별자는 선택값이며, 서버에서 인증된 주체의 해당 팀 권한을 확인해야 한다. 이 원칙을 TA-R08의 조회·저장·엑셀 경계에 적용한다.
- [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html): 보안 토큰의 충분한 무작위성·일회 사용·만료 원칙을 운영진 초대 설계에도 참고한다. 이 자료가 초대 24시간이나 조회 코드 90일을 정한 것은 아니며, 해당 수치는 이 프로젝트에서 제안한 뒤 사용자가 채택한 정책이다.
