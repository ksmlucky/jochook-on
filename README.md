제품명은 **조축ON**, 기존 팀명은 **HANA FC**입니다. 영문 코드명 `jochookOn`, 저장소·패키지 slug `jochook-on`으로 통일합니다. 화면에는 현재 접속한 팀명을 표시하며 선수·경기를 팀별로 분리합니다. 이름 변경의 이력은 [브랜드 변경 명세와 화면 흐름](docs/rebranding.md)에 정리했습니다.

접속 흐름은 **서비스 관리자의 팀 생성·감독 지정 → 감독의 코치 임명 → 감독·코치의 코드와 비밀번호 발급 → 회원 조회**입니다. [요구사항 정의서](docs/team-access-requirements.md), [스토리보드](docs/team-access-storyboard.md), [API 계약](docs/team-access-api.md)에 승인된 정책과 화면·서버 동작을 정리했습니다. 당분간 HANA FC에서 사용하고 복수 포메이션을 지원한 뒤 다른 팀을 도입합니다. **[조축ON 시범 서비스 열기](https://http--jochook-on-web--wmjz5mzg84j4.code.run/)** — 2026-10-14 Northflank 무료 서비스 배포와 실제 DB 이전·로그인 검증을 완료했습니다. [배포 상태·운영 안내](docs/northflank-deployment.md). Oracle 용량 확인은 병행합니다.

실제 선수·경기 입력은 위 공개 주소에서 진행합니다. 로컬 DB와 클라우드 DB는 자동 동기화되지 않습니다. 아이폰은 Safari로 접속해 **공유 → 홈 화면에 추가**로 설치할 수 있으며, 실제 아이폰 설치·재접속 확인은 다음 사용자 점검 단계입니다.

**이 PC에서는 `Start-JochookON.cmd`를 더블클릭한 뒤 <http://127.0.0.1:5173>으로 접속하면 됩니다.** 개발 도구를 C:의 사용자별 프로그램 폴더에 준비했으며, Docker 설정 전에는 Windows용 MySQL 8.4를 사용합니다. 실행·종료·개발 터미널·설치 상태는 [이 PC 실행 안내](docs/local-setup.md)를 먼저 읽어 주세요. 아래 Docker 실행 절차는 Docker가 준비된 환경에서 사용합니다.

## 지금 구현한 범위

- Java 21 / Spring Boot 4.1.1 API, React / TypeScript 화면, MySQL 8.4 실행 설정
- 활동 중인 선수 목록 조회, 페이지 나누기, 입력 범위 검증
- 실제 존재하는 연령대·직책·1지망 포지션 그룹(공격/미드/수비/키퍼) 조합 필터, 전체 결과를 기준으로 정렬·페이징
- 감독·코치의 경기 삭제 전 확인, 등록·수정·삭제의 작업자·전후 내용 보관과 변경 이력 조회 ([정책·화면 흐름](docs/player-filters-and-match-history.md))
- 감독(DIRECTOR)·코치(COACH)·조회 회원(MEMBER) 팀 권한, 세션 로그인·로그아웃과 CSRF 보호
- 로컬 초기 관리자 생성, BCrypt 비밀번호 해시 저장
- 서비스 관리자만 팀 생성·최초 감독 지정, 감독은 기존 계정 코치 임명 또는 24시간 일회용 초대·해제
- 해당 팀 감독·코치만 조회 코드와 숫자 6자리 비밀번호 발급·재발급·폐기, 회원은 90일 유효한 조합으로 계정 없이 조회
- 팀 소속·세션·요청 팀을 서버에서 검증하고 선수·경기·용병·엑셀·자동 편성의 조회와 저장을 팀별로 제한
- 감독·코치 전용 선수 등록·수정, 이름·기본 포지션·선택 등번호와 가입일, 동시 수정 충돌 안내
- 생년·팀 직책 저장, 선수단·경기 명단·쿼터 스쿼드의 연도 기준 나이·연령대 표시
- 선호 포지션 1·2·3지망 저장 (1지망 필수, 2·3지망 선택, 중복 금지). 포지션 미확인(UN)은 세 지망을 비움
- 여러 선수 직접 입력 및 .xlsx 양식 다운로드·업로드·행별 검토·일괄 저장
- 경기 등록·조회·수정, 참불 투표와 실제 출석 구분, 4-1-2-3 쿼터별 직접 배치·득점·도움·코멘트
- 참석 명단 기반 1~4쿼터 자동 계획: 출석 우선권·GK 전용 그룹·연속 휴식 방지·앞 3쿼터 교체 최소화
- 02에서 외부 용병 등록·재선택, 정회원과 구분하여 자동 편성·실제 경기 기록에 반영
- 03 시작에서 계획대로 참석·출전 기록 일괄 저장, 기존 실제 기록 보호
- 하루 4쿼터 자체전: A팀·B팀별 계획·실제 배치, 최종 스코어와 팀별 득점 표시
- 선수 테이블을 만드는 Flyway 마이그레이션
- 화면의 로딩·빈 목록·실패·재시도 상태
- 선수 도메인 / API 권한 / 페이지 검증 테스트, 실제 MySQL용 통합 테스트
- GitHub Actions의 테스트·빌드 작업 정의

초기 DB에는 선수나 경기 예시 데이터를 넣지 않습니다. 선수 활동 종료, 시즌 통계, 가상 몸값은 다음 단계입니다. 현재 로컬 API는 내 컴퓨터(127.0.0.1)에 바인딩되며 선수·경기 기록은 팀 코드 접속 또는 소속 계정 로그인 후 조회할 수 있습니다. 운영용 Docker 구성과 GitHub 업로드·무료 호스팅 검토는 [배포 안내](docs/deployment.md)를 참고하세요. 비밀번호 변경/복구, 공개 팀 가입과 실제 클라우드 배포는 후속 작업입니다.

## 폴더 구조

```text
HANA FC Transfermarkt/
├─ backend/                    # Spring Boot API와 Java 테스트
│  ├─ gradle/wrapper/           # 팀원이 같은 Gradle 버전으로 실행
│  ├─ build.gradle             # Java 버전·의존성·테스트 작업
│  └─ src/
│     ├─ main/java/com/jochookon/
│     │  ├─ JochookOnApplication.java # Spring Boot 시작점
│     │  ├─ auth/              # 계정, 비밀번호 조회, 초기 관리자, 로그인 정보 API
│     │  ├─ config/            # 공통 보안 설정
│     │  ├─ team/              # 팀 생성·소속·초대·조회 코드와 요청 팀 검증
│     │  ├─ player/            # 선수 기능의 Controller·Service·Repository·Entity
│     │  └─ match/             # 경기·투표·출석·쿼터 기록을 함께 관리
│     ├─ main/resources/
│     │  ├─ application.yaml   # DB 연결·서버·JPA 설정
│     │  └─ db/migration/      # Flyway SQL 변경 이력
│     └─ test/java/            # 단위·API·MySQL 통합 테스트
├─ frontend/                   # React 화면
│  └─ src/features/           # auth / teams / players / matches 별 API·상태·화면
├─ scripts/                    # Windows 개발 환경 초기화·API 실행
├─ docs/                       # 설계 이유·학습 순서·개발 단계
├─ .github/workflows/ci.yml     # GitHub에 올린 후 실행되는 검증
├─ compose.yaml                # 로컬 MySQL 컨테이너
├─ .env.example                # DB 설정의 공유 가능한 예시
├─ pnpm-lock.yaml              # 프론트 의존성 버전 고정
├─ work/                       # 로컬 도구·캐시·검증 기록, Git 제외
└─ outputs/                    # 필요할 때 만드는 최종 산출물, Git 제외
```

`outputs/`에는 화면 검증 등의 최종 산출물을 보관합니다. 경기 기록은 `match` 기능에서 투표·출석·쿼터 기록과 함께 처리합니다.

폴더 트리의 최상위 이름은 이 PC의 실제 경로입니다. 로컬 폴더 이동 없이 제품·코드 명칭만 변경하며, 기존 MySQL DB·사용자·볼륨 이름은 연결 호환성을 위해 유지합니다. Java 기본 패키지는 `com.jochookon`, 프론트 패키지는 `@jochook-on/web`입니다.

## 준비물

| 도구 | 필요한 이유 |
| --- | --- |
| JDK 21 | Java 컴파일과 Spring Boot 실행 |
| Node.js 24 | React 개발·빌드 |
| pnpm 11.25.0 | 프론트 패키지 설치, lockfile 재현 |
| Docker Desktop 등 Docker 호환 런타임 | MySQL 8.4와 Testcontainers 실행 |

Docker는 MySQL 실행 환경을 다른 PC·CI와 맞추고, Testcontainers로 일회용 검증 DB를 띄우기 위해 사용합니다. 이 PC에서는 Windows에 설치한 MySQL로 앱을 실행합니다. 2026-10-13 Docker Desktop 엔진 기동과 MySQL Testcontainers 테스트 5개 통과를 확인했습니다. Docker DB로의 실제 데이터 이전은 별도 작업입니다.

pnpm이 없다면 Node.js 설치 후 `npm install --global pnpm@11.25.0`으로 준비합니다. Gradle은 별도 설치 없이 저장소의 Wrapper를 사용합니다. 환경별 정확한 버전은 lockfile과 Wrapper가 고정합니다.

이번 설정 작업에 사용한 검증용 JDK가 `work/tools/`에 남아 있으면 Windows 실행 스크립트가 자동으로 찾습니다. 이 디렉터리는 Git에 포함하지 않으므로 다른 PC나 CI에서는 JDK 21을 준비해야 합니다.

## Windows에서 시작하기

프로젝트 루트에서 PowerShell을 엽니다. Docker 런타임을 먼저 실행하세요.

```powershell
Set-Location "$env:USERPROFILE\Documents\ChatGPT\HANA FC Transfermarkt"

# 최초 1회: 로컬 DB 비밀번호를 생성한다. 기존 .env는 유지한다.
.\scripts\Initialize-Local.ps1

# 최초 1회: 로컬 관리자 초기 정보를 생성한다. 기존 설정을 덮어쓰지 않는다.
.\scripts\Initialize-Admin.ps1

# 최초 1회 또는 의존성 변경 시
pnpm install --frozen-lockfile

# MySQL 기동 및 준비 상태 확인
docker compose up -d --wait

# 이 터미널을 유지한다.
.\scripts\Start-Backend.ps1
```

두 번째 터미널에서 프론트엔드를 실행합니다.

```powershell
Set-Location "$env:USERPROFILE\Documents\ChatGPT\HANA FC Transfermarkt"
pnpm dev
```

- 화면: http://127.0.0.1:5173
- API: http://127.0.0.1:8080/api/v1/players (인증 세션과 현재 팀의 `X-Team-Id` 헤더 필요; 화면이 자동 전달)
- 상태 확인: http://127.0.0.1:8080/actuator/health
- `.local/admin-bootstrap.json`의 username/password로 로그인합니다. 계정 테이블이 비어 있을 때만 최초 관리자를 생성합니다.
- 운영진으로 로그인한 뒤 **선수 등록**을 누릅니다. 이름·기본 포지션은 필수이며 등번호·가입일은 비워 둘 수 있습니다. 선수 카드의 **수정**으로 변경합니다.
- 선호 **1지망은 필수**, 2·3지망은 선택입니다. LB/CB/RB/CDM/CM/LW/ST/RW/GK 중 중복 없이 순서대로 선택합니다. 기본 포지션이 미확인(UN)이면 세 지망을 비웁니다. 그 외 기존 선수는 수정할 때 1지망을 채웁니다.
- **여러 명 입력**: 행 추가 → 입력 내용 검토 → 오류 수정 → N명 전체 등록. 빈 행은 검토에서 제외합니다.
- **엑셀 업로드**: 양식 다운로드 → 첫 행을 유지하고 작성 → .xlsx 업로드 → 화면에서 오류 수정·재검토 → 전체 등록. 열 제목 셀에 필수·선택 여부가 표시되며, 표시가 없는 기존 양식도 업로드할 수 있습니다. 한 번에 200명 / 2MB까지, 시트는 하나만 사용합니다. 날짜는 YYYY-MM-DD 또는 Excel 날짜입니다. 등번호·가입일·2·3지망은 빈칸을 허용합니다.
- 미리보기는 DB를 바꾸지 않습니다. 일괄 등록은 모두 성공하거나 모두 취소됩니다. 기존 선수 수정이나 자동 중복 제거는 하지 않으며, 같은 이름은 경고로 알려 줍니다. 같은 파일을 다시 등록하면 새 선수들이 생기므로 목록을 확인하세요.
- 참석 예정 명단을 확인하면 1~4쿼터 자동 편성을 실행할 수 있습니다. [편성 기준과 구조](docs/automatic-lineup.md)에 교체·휴식·출석률 우선순위와 한계를 설명했습니다.

### 팀을 만들고 회원에게 열기

1. **운영진 로그인**으로 본인의 기존 계정에 접속합니다. 서비스 관리자로 지정된 계정에만 **서비스 팀 관리** 메뉴가 표시됩니다. 기존 HANA FC는 이미 연결할 팀이므로 다시 만들지 않습니다.
2. **서비스 팀 관리 → 팀 생성**에서 팀명과 최초 운영진을 지정합니다. 기존 계정이면 정확한 로그인 ID를 입력해 바로 연결합니다. 새 운영진이면 일회용 초대 링크를 복사해 지정한 사람에게 개인적으로 전달합니다.
3. 새 운영진은 24시간 안에 초대를 열어 자신의 ID·비밀번호를 설정합니다. 이미 가진 계정을 쓸 때는 그 계정으로 로그인하고 수락합니다. 첫 운영진이 활성화되어야 팀을 사용할 수 있습니다.
4. 운영진이 본인 팀의 **팀 접속 코드 관리**에서 **코드·비밀번호 발급**을 누릅니다. 12자 코드와 숫자 6자리 비밀번호가 함께 생성되고 90일 동안 유효합니다. 두 원문은 발급 직후 한 번만 표시하므로 복사해 팀원에게 직접 공유합니다. 다시 볼 수 없으면 재발급합니다. 최근 20건의 발급·재발급·폐기 담당자와 시각을 이력에 남깁니다.
5. 회원은 조축ON 홈에서 코드와 비밀번호를 함께 입력해 해당 팀의 선수단·경기 기록을 조회합니다. 등록·수정·엑셀·코드 관리는 운영진만 가능합니다. 재발급·폐기 이후 기존 조합과 그 조회 세션은 다음 요청부터 사용할 수 없습니다. [비밀번호 정책·검증](docs/team-code-password.md)

조회 세션은 유휴 24시간·최대 7일, 개인 계정 세션은 유휴 30분입니다. 여러 팀에 소속된 운영진은 **내 팀 목록**에서 전환합니다. 작성 중이면 확인 후 전환하며 다른 탭에서 팀이 바뀐 이전 초안의 저장도 서버에서 차단합니다. 서비스 관리 권한만으로 모든 팀의 선수·경기나 코드를 열람할 수는 없습니다.

서비스 관리자 지정은 `JOCHOOK_ON_SERVICE_ADMIN_USERNAME`에 활성 계정 ID를 명시합니다. 이 PC의 `Start-JochookON.cmd`는 기존 비공개 관리자 설정을 읽어 해당 계정을 지정하며 모든 ADMIN을 승격하지 않습니다. 새 서버 설정과 기존 데이터 이전 순서는 [배포 안내](docs/deployment.md)를 따릅니다.

### 경기 기록 사용하기

**자체전:** 새 경기의 유형을 **자체전 · A팀 vs B팀**으로 선택하면 하루 전체 4쿼터가 자체전이 됩니다. 02에서 쿼터와 팀을 선택해 각 팀의 4-1-2-3을 직접 채우세요. 다른 팀에 이미 배치된 선수는 먼저 해제해야 하며 다른 쿼터에는 팀을 바꿀 수 있습니다. **이전 쿼터 양 팀 계획 복사**는 양 팀을 함께 복사합니다. 양 팀의 균형을 맞추는 자동 편성은 후속 기능이며 외부 경기의 자동 편성은 계속 사용할 수 있습니다.

03의 **02 계획대로 참석·출전 기록 저장**은 양 팀을 함께 반영합니다. 실제 기록도 A/B팀을 전환해 득점·도움·교체를 입력하고, 04에서 **A팀 득점 : B팀 득점**으로 4쿼터 합계 스코어를 직접 저장합니다. 합계 차이 안내는 각 팀별로 표시합니다. 교체 0.5쿼터 계산은 같은 팀·자리 안에서만 하며 출석은 경기당 한 번입니다. 목록에는 자체전 표기와 득점자의 팀별 골 수가 나옵니다. 배치·스코어 입력 후 또는 최초 저장 후에는 경기 유형을 변경할 수 없습니다.

자체전 엑셀 입력은 기존 양식을 팀별로 작성한 뒤 03에서 해당 팀을 선택해 각각 업로드합니다. 선택한 팀의 4쿼터만 교체하며 다른 팀의 기록은 유지합니다. 같은 쿼터의 양 팀 중복 선수는 반영을 막습니다.

1. 로그인 → 상단 **경기 기록** → **경기 기록 등록**. 날짜와 시작 시간은 필수이며 **시(00~23)**와 **분(00/30)**을 따로 선택합니다. 둘 다 선택해야 저장할 수 있습니다. 상대 팀·장소는 선택입니다. 목록과 입력 화면에 시작 + 2시간을 표시하며 자정을 넘기면 ‘다음 날’로 표시합니다. 기존 미입력/30분 단위가 아닌 시간은 보존하고 다음 수정·저장 시 선택해야 합니다. 종료 시간·쿼터 길이를 별도 저장하지 않습니다.
2. 이름·등번호 검색과 체크로 참석 예정자를 선택합니다. ‘선택한 선수만 보기’로 대조하고 아래 상세 표에서 불참·미정도 입력할 수 있습니다. 체크 해제는 미투표로 되돌립니다. 투표만 먼저 저장할 수 있고 실제 출석은 미확인으로 남습니다. **참석 명단 확인 · 1~4쿼터 자동 편성**을 누르면 선호와 과거 출석률을 반영해 02 계획을 채웁니다. GK는 1~3지망에 GK가 있는 선수끼리, 필드는 별도로 나눕니다. 두 쿼터 연속 휴식을 막고, 앞 3쿼터 교체를 최소화하며 개인 출전량 차이는 그룹 내 최대 1쿼터입니다. 결과 표의 출석률·휴식·비선호 배치를 확인하세요. 경기 전 계획에서는 선수를 드래그하거나 선수 → 자리 순서로 클릭해 1~4쿼터를 채웁니다. 끌고 있는 선수 카드가 포인터를 따라 움직이며 가능한 배치 자리를 강조합니다. 현재 쿼터에 배치한 후보는 초록 배경과 ‘배치 완료·자리·선발/교체’로 구분합니다. 선발/교체, 자리 교환, 이전 쿼터 복사와 총 예정 쿼터를 지원합니다. 02 아래 **계획 저장 · 실제 기록으로**를 누르면 저장하고 03으로 이동합니다.
3. 용병이 있으면 02의 **+ 용병 추가**에서 이름과 선택 등번호·생년·선호 포지션을 입력하거나 기존 용병을 선택합니다. 이름만으로도 등록할 수 있으며, 포지션 미확인은 자동 편성에서 제외됩니다. 용병 프로필은 등록 즉시 DB에 저장되고 경기 참석 예정·배치는 계획 저장 시 반영됩니다. 정회원 선수단에는 표시하지 않으며 다음 경기에서 같은 용병을 재선택할 수 있습니다. 번호를 입력하면 정회원과 동일하게 같은 팀 활동 선수 간 중복을 막습니다.
4. 경기 후 계획대로 진행했다면 03 시작의 **02 계획대로 참석·출전 기록 저장**을 누릅니다. 참석 예정자 중 미확인을 참석으로 처리하고, 선발·교체를 포함한 1~4쿼터 계획을 실제 기록으로 저장합니다. 골·도움은 0으로 시작합니다. 기존 지각·불참은 유지하고 계획에 실제 불참자가 있으면 저장을 멈춥니다. 실제 출전 기록이 하나라도 있으면 재복사를 막으므로 이후에는 직접 수정합니다. 당일 인원이 달라졌다면 먼저 ‘투표 상세·실제 출석 입력 펼치기’에서 출석과 배치를 확인하세요.
5. 1~4쿼터 탭에서 실제로 뛴 선수를 4-1-2-3 자리에 직접 선택하고 득점·도움을 기록합니다. 각 자리에 선발 1명과 교체 1명을 넣을 수 있습니다. 교체는 선발 배치 후 **+ 교체 선수 추가**로 선택하며, 실제 교체 선수가 있을 때만 교체 입력란·인원 수를 표시합니다. 교체한 두 선수는 각 0.5쿼터, 교체 없는 선발은 1쿼터로 계산합니다. 같은 선수는 한 쿼터에 한 번만 배치합니다. 03 아래 **출전 기록 저장 · 집계 확인**으로 저장하고 04로 이동합니다.
6. **04 결과·코멘트**에서 4쿼터 합계 **우리 팀 득점 : 상대 팀 득점**을 직접 입력하고 코멘트를 남깁니다. 스코어는 양쪽 모두 0~99 또는 모두 빈칸이며 미입력은 0:0과 다릅니다. 선수별 득점 합계와 달라도 안내만 표시하고 저장할 수 있습니다. **경기 기록 저장** 후 목록에 스코어와 등번호순 득점자 최대 3명(나머지는 외 N명)이 표시됩니다. 번호 없는 득점자는 마지막입니다. 목록은 10개씩 표시하고 저장된 카드는 다시 수정할 수 있습니다. 회원은 조회만 가능합니다.

01 투표·출석 / 02 스쿼드 계획 / 03 실제 출전 / 04 결과·코멘트 탭으로 이동합니다. 한 번에 한 단계만 보여주며 작성 중인 값은 탭을 바꿔도 유지됩니다. 하단 고정 **경기 기록 저장**은 현재 단계와 관계없이 전체 입력을 저장합니다. 자동 편성의 상세 출석률 표는 필요할 때 펼쳐 봅니다.

단계별 저장 버튼은 그 시점에 입력한 경기 내용 전체를 같은 API로 저장하며 경기 확정 처리는 아닙니다. 저장 성공 시 오른쪽 위에 반투명 알림이 나타나고 4초 뒤 자동으로 사라집니다. 02 계획 저장·03 계획대로 저장·03 출전 기록 저장·최종 저장에 적용하며, 입력 오류와 저장 실패 안내는 화면에 유지합니다. 화면을 유지하고 저장 응답의 ID/version을 다음 저장에 사용하므로 새 경기가 중복 생성되지 않습니다. 계획은 실제 출석·기록으로 자동 전환되지 않습니다. 경기 화면에서는 선수를 `#등번호 이름`으로 표시하며 번호가 없으면 ‘등번호 없음’으로 표시합니다. 내부 선수 ID는 연결과 저장에만 사용합니다.

**엑셀로 4쿼터 한 번에 입력:** 경기 편집 화면의 **경기 엑셀 양식 다운로드** → `쿼터기록` 시트 작성 → 업로드 → 행별 오류 확인 → **검토한 엑셀로 4쿼터 초안 교체** → 실제 출석 확인 → **경기 기록 저장**. 반영하면 기존 4쿼터 초안 전체를 교체하므로 입력하지 않은 쿼터는 비워집니다. 기본 정보·투표·출석·코멘트는 유지합니다. 미리보기와 초안 반영은 DB를 바꾸지 않습니다.

양식에는 쿼터·포지션·선발/교체가 미리 채워져 있습니다. 이름은 필수, 등번호·득점·도움·선수 ID는 선택이며 각 열 제목에도 표시합니다. 등록된 선수의 이름을 사용하고 동명이인은 등번호나 선수 ID로 구분하세요. CB는 LCB/RCB, CM은 LCM/RCM 자리로 구분합니다. .xlsx 2MB, 최대 88명분의 쿼터 기록을 지원하며 이름·스탯이 빈 배치 행은 제외합니다. 오류는 엑셀에서 고쳐 다시 올립니다. 선수 자체를 추가하려면 선수단 등록을 먼저 사용합니다.

쿼터 길이·교체 시각은 저장하지 않습니다. 교체는 같은 자리의 1:1 교체만 지원하며 재투입·쿼터 내 포지션 이동은 지원하지 않습니다. 프로 비교의 **4쿼터=1경기**는 추후 결정할 후보입니다. 빈 자리는 미기록, 입력한 선수의 득점·도움 기본값은 0입니다. 집계는 입력한 기록 기준이며 기록 확정·시즌 순위는 후속 단계입니다. 별도 모임 등록, 용병 전용 프로필 수정·활동 종료 화면, 카카오톡 자동 연동은 아직 없습니다. 저장 응답을 잃거나 수정 충돌이 발생하면 재전송을 멈추고 입력 내용을 보관한 뒤 목록에서 최신 기록을 확인하세요.

프론트엔드는 `/api` 요청을 Vite 개발 서버를 통해 8080으로 전달합니다. 따라서 로컬 개발에서 브라우저용 CORS 허용 범위를 넓힐 필요가 없습니다. 이것은 개발용 프록시이며, 배포할 때는 정적 파일 서빙과 `/api` 라우팅을 별도로 구성합니다.

`Start-Backend.ps1`은 `.env`의 DB 설정과 `.local/admin-bootstrap.json`의 초기 관리자 설정을 읽어 현재 프로세스 환경변수로 전달합니다. Spring Boot가 이 파일들을 자동으로 읽는 것은 아닙니다. IntelliJ에서 직접 실행할 때는 같은 DB 환경변수를 Run Configuration에 설정하세요. 이미 관리자 계정이 생성됐다면 초기 관리자 환경변수는 필요 없습니다. `.env` 값은 생성된 단순 문자열 형식을 사용하며, Compose 변수 치환식이나 다중 행 값은 이 스크립트가 처리하지 않습니다.

MySQL 포트는 기존 3306과 충돌할 가능성을 줄이도록 3307을 사용합니다. 바꾸려면 `.env`의 `MYSQL_PORT`를 수정한 뒤 DB와 API를 재시작하세요. DB 데이터는 Docker의 `mysql-data` 볼륨에 보관됩니다. 이미 생성된 볼륨의 DB 비밀번호는 `.env`만 바꿔도 변경되지 않습니다.

종료는 API·프론트 터미널에서 각각 `Ctrl+C`, DB는 `docker compose stop`을 사용합니다.

## 홈 화면에 설치해서 사용하기 (PWA)

스토어 등록비 없이 홈 화면에 추가하는 PWA를 유지하면서 Capacitor 8.5.3 앱 프로젝트 준비도 시작했습니다. Android/iOS 프로젝트와 서버 미연결 안내 화면은 준비됐지만 실제 앱 빌드·인증·API·스토어 배포는 아직 완료하지 않았습니다. 개발자 계정 비용은 나중에 결정합니다. [앱 준비 구조·명령](frontend/NATIVE.md). 서버·도메인 비용은 별도이고 공개 서버 연결은 아직 준비 중입니다.

- 공개 HTTPS 주소가 준비되면 아이폰 Safari의 **공유 → 홈 화면에 추가**를 선택하세요. **웹 앱으로 열기** 옵션이 보이면 켜고 추가합니다.
- 안드로이드 Chrome에서는 **메뉴 → 앱 설치 / 홈 화면에 추가**를 선택합니다. 지원 브라우저에서는 화면의 **조축ON 설치** 버튼도 제공됩니다. 메뉴 이름은 기기·브라우저마다 다를 수 있습니다.
- 카카오톡 안에서 링크를 열었다면 Safari/Chrome으로 다시 여세요. 홈 화면에 추가한 앱에서 팀 코드를 다시 입력해야 할 수 있습니다. 기존 접속 만료·코드 폐기 정책은 그대로 유지합니다.
- 기록 조회·저장에는 인터넷이 필요합니다. 서비스 워커는 개인정보 없는 `/offline.html` 안내만 캐시하고 API·인증·선수·경기·앱 HTML을 따로 저장하지 않습니다. 화면이 갑자기 바뀌지 않도록 업데이트 때문에 강제 새로고침하지 않습니다.

설치 정보는 `frontend/public/manifest.webmanifest`, 아이콘은 `frontend/public/icons/`, 설치 안내는 `frontend/src/features/install/`에 있습니다. 축구공과 ON을 결합한 로고를 사용하며 `scripts/Generate-PwaIcons.ps1`로 다시 생성할 수 있습니다. 서비스 워커는 배포 빌드와 보안 연결에서만 등록하며 `pnpm dev`에서는 새로 등록하지 않습니다. 개발 중 기존 등록이 남아 있다면 다른 로컬 포트를 쓰거나 개발자 도구에서 해당 등록을 해제하세요.

로컬 PC의 `http://127.0.0.1:5173`에서는 설치용 파일을 검증할 수 있지만 아이폰에서 이 주소는 아이폰 자신을 뜻합니다. 실제 휴대전화 설치는 [Oracle·Cloudflare 배포 안내](docs/oracle-cloudflare-deployment.md)에 따라 공개 HTTPS 주소를 만든 뒤 확인합니다. [PWA 계획·화면 흐름](docs/mobile-app-plan.md)과 [검증 기록](docs/verification.md)을 참고하세요.

## 검증하기

```powershell
# Docker 없이 실행할 수 있는 도메인·API 테스트
.\scripts\Start-Backend.ps1 -Task test

# Docker 필요: 격리된 MySQL에서 Flyway → JPA → API 전체 확인
.\scripts\Start-Backend.ps1 -Task integrationTest

# 연령대 경계·한국 기준 연도 계산 테스트 (Node 24)
pnpm --filter @jochook-on/web test

# 배포용 파일 생성
.\scripts\Start-Backend.ps1 -Task bootJar
pnpm build
```

MySQL 통합 테스트는 로컬 운영 DB에 접속하지 않고 Testcontainers가 만든 일회용 DB를 사용합니다. Docker가 없으면 명시적으로 실패합니다. `test` 성공만으로 MySQL 통합 테스트까지 성공했다고 판단하지 않습니다. GitHub Actions는 두 종류의 테스트를 모두 실행하도록 작성했습니다. 워크플로 실행 결과는 실제 GitHub 실행 후 확인해야 합니다.

Java 결과물은 `backend/build/libs/`, 화면 결과물은 `frontend/dist/`에 생깁니다. `pnpm build`는 프론트엔드만 빌드합니다.

이번 설정 작업에서 실제로 통과한 검증과 아직 실행하지 못한 항목은 [검증 기록](docs/verification.md)에 구분해 적었습니다.

## 함께 배우는 순서

기능을 추가할 때는 기획이 간단한 기능 명세·스토리보드를 작성하고, 디자인·퍼블리싱·프론트와 백엔드가 API 형식과 담당 파일을 합의해 구현합니다. 총괄이 통합과 검증을 조율하고 사용자는 실제 팀 운영 흐름으로 확인합니다. 작은 수정은 문서를 간소화하며, 세부 협업 기준은 [AGENTS.md](AGENTS.md)를 따릅니다.

선수단 조회는 **등번호 오름차순·20명·카드 보기**가 기본입니다. 목록 위에서 카드/표, 10/20/30명, 등번호/나이/이름/선호 포지션과 정렬 방향을 선택하세요. 선호 포지션순은 **1지망 기준 골키퍼 → 수비 → 미드 → 공격** 또는 역순이며, 같은 그룹은 등번호 오름차순입니다. 정렬·페이지 크기를 바꾸면 첫 페이지부터 표시합니다. 서버가 전체 명단을 먼저 정렬하므로 다음 페이지에서도 순서가 이어집니다. 생년·등번호·1지망 미입력은 해당 정렬의 양방향 모두 마지막에 표시합니다. 표는 좁은 화면에서 가로 스크롤할 수 있습니다.

직책은 **정회원·코치·감독·총무·회장** 중 하나를 선택하며 미입력은 정회원입니다. 생년은 4자리 직접 입력과 목록 선택을 모두 지원합니다. 수정/일괄 입력 중 **선수단 보기** 또는 상단 **선수단**을 누르면 확인 후 조회로 돌아갑니다. 취소하면 입력을 유지하고, 요청 처리 중에는 이동을 막습니다. 선수 카드/표는 1지망을 기준으로 LW/RW/ST 빨강·CM/CDM 초록·LB/CB/RB 파랑·GK 황금색으로 표시합니다. 쿼터 자리는 해당 자리의 포지션 색으로 표시합니다.

PK는 고정된 선수 ID를 유지합니다. 같은 팀의 활동 선수끼리 등번호가 겹치면 단일 등록·수정·일괄/엑셀 등록을 거부하며 DB에서도 방지합니다. 번호 없는 선수는 여러 명 허용하고 활동 종료 선수의 번호는 재사용할 수 있습니다. 활동 종료·복귀 화면 자체는 후속 단계입니다. 기존 명단의 가입일 일괄 변경은 운영 데이터 변경이며 신규 선수의 가입일 기본값을 고정하는 기능은 아닙니다. 득점·도움·출전 쿼터 정렬은 시즌 통계 단계의 할 일로 기록했습니다.

생년은 `players.birth_year`, 팀 직책은 `club_role`에 저장합니다. 나이는 저장하지 않고 **기준 연도 − 생년**으로 계산합니다. 생일과 관계없이 1996년생은 2026년에 연도 기준 30세·30대입니다. 선수단은 현재 한국 연도, 경기 화면은 경기 날짜의 연도를 사용합니다. 생년이 없으면 연령대 미확인으로 표시합니다. 이는 만 나이 계산이 아닙니다.

포지션을 모르면 기본 포지션을 **미확인(UN)**으로 선택합니다. 선호를 임의로 채우거나 비활동으로 바꾸지 않습니다. 알게 되면 수정 화면에서 포지션과 1지망을 입력하세요. 선수 등록용 엑셀에는 선택 생년·직책 열을 추가했으며 기존 7열 양식도 읽을 수 있습니다. 팀 직책은 로그인 권한과 별개입니다. 실제 명단은 로컬 DB와 Git 제외 경로에만 보관하며 공개 샘플이나 Flyway SQL에 넣지 않습니다.
